## Research

**No web source was consulted and no network access was made.** Every semantic
question this task could raise is settled by documents already in the repository:

* the arithmetic, verbatim — `.plan/DIAGNOSTIC_ARCHITECTURE.md` §3.1;
* the rounding mode, named explicitly — same section;
* every degenerate case — same section's table, plus `TASK.md` §Error Handling;
* the clamped-never-padded rule — the same section, and
  `q_tensor_runtime::BlockExtent::clamped_to` in code;
* which schemes refuse and under which ID — §3, `.plan/PRODUCT_SCOPE.md`,
  `QUANT-011`;
* the fidelity vocabulary — `.plan/DATA_ARCHITECTURE.md` §8;
* the rank ceiling — `docs/decisions/ADR-010-tensor-rank-ceiling.md`.

**Four** questions were genuinely undetermined by the repository and were
resolved from the documents by reasoning rather than by a web source. Each is
recorded because each changed the implementation:

1. **Where does the integer code index get formed?** §3.1 writes
   `clamp(round_half_to_even(x / s) + z, 0, n - 1)` without naming a type. Doing
   the `+ z` in `f32` loses the low bits of the sum for a large zero point, so
   the two implementations would disagree on a value *neither had rounded*. It is
   done in `f64` and then `i64` in both, where it is exact for every `i32` zero
   point and every integer-valued `f32` quotient. Recorded in
   `crates/q-quant/src/rtn.rs`'s module docs and in the reference script's
   docstring. **This changed the implementation.**
2. **What happens to a constant *non-zero* unit under `asymmetric`?** §3.1
   tabulates `max|g| == 0`, which under `symmetric` is the only unit whose scale
   is zero. Under `asymmetric` the scale is `(max − min) / (n − 1)`, which is
   zero for **any** constant unit, so a rule is needed whenever `max == min`.

   The rule is **`s = |c|`** for a constant `c ≠ 0`, and the tabulated `s = 1`
   only for `c == 0`. §3.1's zero-point and code formulas are left untouched, so
   the deviation is one line: `z = round_half_to_even(−c/|c|)` comes out as `∓1`
   and `x̂ = ±|c| = c` **bit-exactly**, for both signs and every magnitude. The
   alternative — refusing — would refuse an all-ones norm weight that is exactly
   representable.

   **This was first implemented as `s = 1` and that was wrong.** See
   `### Defects found and fixed before commit` below: at `s = 1` §3.1's own formulas send a
   constant `0.5` to `0.0` and a constant `0.823457` to `1.0`, silently, while
   `symmetric` reconstructs both exactly. **This changed the implementation, and
   the same rule is in the reference script**, or the goldens would diverge
   exactly there.

3. **Is a normal scale enough to satisfy "never silently produce infinities"?**
   No, and §3.1 does not say it is — the clause sits on the subnormal row, but the
   requirement is about the output. `(q − z) · s` can overflow `f32` while the
   scale is perfectly normal and every input is finite. A **non-finite
   reconstruction is refused**, naming the unit and the index. It can only be
   detected per value, so the output buffer's contents are unspecified when that
   refusal is returned; every other refusal precedes execution and leaves the
   buffer untouched. **This changed the implementation and the reference script.**
4. **Where does `Precision::Nf4` live?** `TASK.md` §Test Cases row 8 spells it
   `Precision::Nf4`, while §Data Contracts fixes `Precision { Int8, Int4 }`.
   `.plan/DIAGNOSTIC_ARCHITECTURE.md` §3 ("NF4 and MXFP4 are named variants of
   `QuantScheme` that refuse with `QUANT-011`") and `.plan/PRODUCT_SCOPE.md`
   ("`QuantScheme` is an open enum … v1 implements RTN only and names the others
   in the refusal") both put it on `QuantScheme`. Implemented as
   `QuantScheme::Nf4`; `Precision` stays closed at two variants exactly as the
   data contract fixes it. **This changed the implementation.**

### Defects found and fixed before commit

Recorded because a reviewer should know the goldens alone did **not** catch these
— both implementations agreed on the wrong answer, which is exactly the shared
misconception a differential test cannot see. Both were found by writing a test
that swept a *range* of constant magnitudes rather than the single magnitude the
first golden happened to use.

**Defect 1 — a constant non-zero unit under `asymmetric` reconstructed wrongly.**
The first implementation used `s = 1` for a zero-dynamic-range unit, in both Rust
and the reference. Measured, before the fix:

```
Asymmetric c=0.5    -> scale=1 zero=0  out[0]=0        exact=false
Asymmetric c=-0.3   -> scale=1 zero=0  out[0]=0        exact=false
Asymmetric c=0.7071 -> scale=1 zero=-1 out[0]=1        exact=false
Asymmetric c=1      -> scale=1 zero=-1 out[0]=1        exact=true
Symmetric  c=0.5    -> scale=0.0714286 zero=0 out[0]=0.5 exact=true
Symmetric  c=-0.3   -> scale=0.0428571 zero=0 out[0]=-0.3 exact=true
Symmetric  c=0.7071 -> scale=0.1010143 zero=0 out[0]=0.7071 exact=true
```

A constant `0.5` reconstructing to `0.0` is a 100% error; `0.7071 → 1.0` is 41% in
the wrong direction. Constant biases and norm weights are common, so this is a
live wrong number, not a corner case. `c = 1` is the one magnitude where `s = 1`
and `s = |c|` coincide — and it was the only constant magnitude in the golden set,
so the golden confirmed the rule at the single point where the rule was invisible.
The tell was that the two zero-point modes disagreed on the same tensor.

**A note on the constant, so a grep does not mislead.** The probe above ran at
`0.7071`. The committed golden and test use **`0.823457`** instead, changed only
because `clippy::approx_constant` flags `0.7071` as an approximation of
`f32::consts::FRAC_1_SQRT_2` under `-D warnings`. `0.823457` exhibits the
identical defect — it too reconstructed to `1.0` under `s = 1`, verified before
the change — so grepping the committed tree for `0.7071` finds nothing, and
`0.823457` is where to look.

Fixed to `s = |c|` in **both** implementations. Consequences, all now tested:
constants round-trip bit-exactly at every magnitude under `asymmetric`; a constant
*subnormal* unit now refuses on §3.1's existing subnormal-scale row, which is what
`symmetric` already did with the same input; and a constant at `−4e9` is now exact
rather than refused, so the zero-point-overflow refusal moved to a construction
that actually reaches it (`[−1e30, −1e30 + 1 ULP]`, `z = 3374896640`).

**Defect 2 — a finite input could reconstruct to `±Inf`.** Found by the same
sweep. Both implementations produced `inf` for a constant unit at `±f32::MAX`
under int8 symmetric: `s = f32::MAX/127` is a perfectly **normal** `f32`, but
`127 · s` rounds up past `f32::MAX`. §3.1 says "never silently produce
infinities", so this is a defect regardless of which row the clause sits on.

Fixed by refusing a non-finite reconstruction — `QuantError::ReconstructionNotFinite`,
kind `reconstruction_not_finite` — in both implementations. Deliberately **not**
a parameters-only pre-check: the reachable-code bound would refuse cases that work
(asymmetric `f32::MAX` reconstructs exactly, because its reachable code is 0), and
`s = f32::MAX` with ordinary inputs reconstructs to `0.0` rather than overflowing.
Both of those are asserted, so a future defensive over-refusal fails.

**Secondary — one parameter pair applied to a `PerGroup` config.** `simulate` and
`simulate_into` silently ignored the grouping and behaved per-tensor. Now
`config_rejected`, naming `simulate_per_group_into`. `QM-0122` constructs configs
and parameters separately, so this is the mistake it can actually make.

## Summary

`crates/q-quant` is a new crate with **no dependency on any Quatricmorph crate**
— values in, values out. `cargo tree -p q-quant` shows `serde` and `thiserror`
only, plus `serde_json` as a dev-dependency for reading the committed golden;
`grep -rn "std::fs\|std::io\|File::\|std::net\|std::path\|env::" crates/q-quant/src/`
returns nothing. `TASK.md` §Risks names a dependency on `q-source` here as a
review failure, which is why the crate carries its own `QuantError` rather than
importing `q_source::error::QError`.

**Binding ADRs.**

* **ADR-010 — rank ≤ 3 is implemented; higher rank refuses rather than
  flattens.** `QuantConfig::validate_for_shape` refuses rank > 3 with
  `NotImplemented` carrying `GRID-007`, and `rank_above_three_is_refused_rather_than_flattened`
  asserts rank 0–3 accepted and rank 4 and rank 9 refused. This is the only place
  granularity-versus-shape validation can live in a crate that never sees a
  tensor: the caller holds the shape, this crate holds the rule.
* **ADR-011 — content-derived identifiers.** Not applicable: this crate mints no
  identifier and persists nothing.

**Applicable §19 checks.** §19's four prohibitions are about GLB geometry, browser
dumps, Cesium-as-compute and terabyte chat expressions, none of which this crate
can do — it has no renderer, no HTTP surface and no file access. The one that does
bind is §19's last: **"Do not assume a color pattern corresponds to a semantic
concept."** Its generalisation is honoured literally — nothing in
`crates/q-quant` describes a pattern of quantisation error as telling anyone what
a tensor means or what a layer does. The crate docs state it: *"Quantisation error
is arithmetic. It says nothing about what a tensor means or what a layer does, and
nothing in this crate claims otherwise."*

**`AGENTS.md` rule 4** — "distinguish exact vs sampled vs approximate" — is met
through `.plan/DATA_ARCHITECTURE.md` §8's own vocabulary rather than a parallel
scheme, matching what `QM-0020` landed in `q_statistics::StatisticsFidelity`:

* §8's `quantized` — *"values present but lossily encoded"* — is the label for a
  reconstruction. It is §8's word for what `AGENTS.md` calls approximate, and it
  is the honest one here: the loss is the substance of this crate.
* §8's `exact` — *"the values as stored in the checkpoint"* — is earned **only**
  when every reconstructed value equals its input bit-for-bit. Derived from
  `to_bits()` equality, never asserted by a caller.
* §8's `aggregate` and `sampled` are deliberately **not** spellable here and the
  test `the_fidelity_mapping_is_total_and_cannot_be_asserted_by_a_caller` proves
  it: this crate produces values, not statistics over them.

**The minimal consistent extension of §3.1's table** — zero dynamic range under
`asymmetric`, not only the all-zero unit — is `## Research` item 2. It is in both
implementations and is the reason `constant_ones_int4_asymmetric` is a golden.

**Boundary conformance, checked rather than asserted.** `cargo tree -p q-quant`
lists no Quatricmorph crate at all. The §Risks row ("a dependency on `q-source`
here is a review failure") and the §Completion Evidence line ("`q-quant`'s
dependency list contains no I/O crate") are both satisfiable by inspection of
`crates/q-quant/Cargo.toml`, which says so in a comment.

### Bit-exact versus toleranced — the real figures

**There is not one toleranced comparison in this task.** Every comparison against
the reference is on `f32::to_bits()`. The measured maximum divergence across
**8 686 reconstructed values and 18 derived scales is 0 ULP** — printed by
`the_measured_divergence_from_the_reference_is_zero_ulp_across_every_golden_value`
and reproduced above.

That is not luck, and it is not a tolerance chosen to pass. IEEE-754
single-precision divide, multiply, subtract and `roundToIntegralTiesToEven` are
all correctly rounded, both implementations perform the same operations in the
same order on the same `f32` inputs, and NumPy's `float32` arithmetic is the same
IEEE single precision. Where a step could have diverged — forming
`round_half_to_even(x/s) + z` — it is done in `f64`/`i64` in **both**
implementations, where it is exact for every value that can land inside the code
range (`## Research` item 1). Had a tolerance been needed, it would have been
evidence of an operation-order difference to fix rather than a bound to pick.

Counted from the golden file: **13 of the 21** numeric cases are bit-exact round
trips — the input is reproduced exactly — namely
`minus_one_zero_one_int8_symmetric`, `all_zero_int8_symmetric`,
`all_zero_int8_asymmetric`, `constant_ones_int4_asymmetric`,
`constant_half_int4_asymmetric`,
`constant_negative_three_tenths_int8_asymmetric`,
`constant_irrational_int4_asymmetric`, `constant_irrational_int4_symmetric`,
`constant_f32_max_int8_asymmetric`, `constant_negative_f32_max_int4_symmetric`,
`constant_large_negative_int8_asymmetric`,
`large_but_valid_zero_point_int8_asymmetric` and
`exactly_representable_int8_symmetric`. The other **8**, and **all 3** grouped
cases, are lossy and are labelled `quantized`. The reference independently
recorded the same exactness flag for each, and
`dequantising_every_golden_unit_reproduces_the_reference_bit_exactly` asserts that
`q-quant`'s derived label agrees with it — so a reconstruction cannot be labelled
exact unless two independent implementations both say every bit survived.

## Claim limits

* **This crate SIMULATES quantisation and has NOT been validated against any real
  quantised checkpoint.** It computes `Ŵ = dequant(quant(W, config))` from
  base-precision values, exactly as `.plan/DIAGNOSTIC_ARCHITECTURE.md` §1
  specifies for v1. It has never read a GPTQ, AWQ, `compressed-tensors` or GGUF
  artifact — that is the `QUANT-010` seam — and nothing here has been compared
  against what any real quantiser would produce for the same tensor. Agreement is
  with a NumPy implementation of the **same specified formula**, which is a check
  on the arithmetic, not on the choice of scheme. `Provenance` has one variant so
  that no downstream surface can accidentally claim otherwise.
* **Which results are exact, and which are not.**
  * **Exact:** the derived scales and zero points; the group extents and counts;
    the reconstruction *arithmetic* (bit-identical to the reference, 0 ULP over
    8 686 values); the round trip of an input that is already a code times the
    scale, labelled `QuantFidelity::Exact` only when every bit survived.
  * **Not exact — `quantized` in `.plan/DATA_ARCHITECTURE.md` §8's vocabulary:**
    every reconstruction of a value that is not exactly representable at the
    target precision. **8 of the 21** numeric golden cases and **all 3** grouped
    cases are in this class. The reconstruction *error* is a real loss and is
    never presented as an exact value; the label is derived from bit equality
    rather than asserted.
  * **Sampled:** nothing here is sampled. Every function reads every value it is
    handed, so §8's `sampled` does not arise and is not spellable in this crate.
* **No GPU.** No Metal, no CUDA, no device code, no `q-gpu` dependency. This is
  CPU arithmetic in safe Rust, and it is the reference the accelerated backends
  will eventually be checked against (`.plan/DIAGNOSTIC_ARCHITECTURE.md` §4.3),
  not something checked against them.
* **No benchmark.** No timing, throughput, latency or peak-RSS number was
  measured or is claimed. The allocation figures (0 allocations for
  `simulate_into`; 1 × 16 384 bytes for `simulate` over a 4096-value unit) are
  **counts**, not a performance measurement, and they say nothing about wall
  time.
* **Nothing about deployment or partner behaviour.** No deployment was performed,
  no environment was configured, and no design partner has seen any of this.
  Nothing here supports a claim about how a real checkpoint, a real user or a real

### Ruling on deviation 1 — `s = |c|` instead of `s = 1`

**Correct deviation. Not blocking.**

§3.1's degenerate table has one zero-dynamic-range row, and its condition is
`max|g| == 0` — the all-zero group. A constant **non-zero** unit has
`max|g| != 0`, so that row does not reach it. Under §3.1's literal asymmetric
formula such a unit gets `s = (max − min)/(n − 1) = 0`, and the next step divides
by it. **§3.1 therefore does not specify `s = 1` here; it specifies nothing at
all.** The implementer is filling a genuine gap, not contradicting a stated
value, so no ADR is required to depart from a rule that does not exist.

`s = |c|` is the choice consistent with the adjacent row's own outcome: the
all-zero row's `s = 1, q = 0, x̂ = 0` reproduces its input exactly, and `s = |c|`
extends exactly that property to every constant magnitude while leaving §3.1's
zero-point and code formulas untouched. I re-derived both branches myself in an
independent driver:

```
c=0.5      asym int4 : s=0.5      z=-1 -> 0.5      bit-exact
c=-0.3     asym int8 : s=0.3      z=+1 -> -0.3     bit-exact
c=0.823457 asym int4 : s=0.823457 z=-1 -> 0.823457 bit-exact
```

and I recomputed what `s = 1` would have produced, by hand from §3.1's formulas:
`0.5 → 0.0` (100 % error), `-0.3 → 0.0` (100 %), `0.823457 → 1.0`. So the defect
was real. I also confirmed the all-zero unit still receives §3.1's **tabulated**
`s = 1, z = 0` under both zero points, and that a constant *subnormal* unit now
refuses on §3.1's existing subnormal-scale row.

The claim that the goldens were blind to this is correct: at `c = 1`, `s = 1` and
`s = |c|` coincide, and `constant_ones_int4_asymmetric` was the only constant
magnitude in the first set.

**Recommendation (non-blocking):** the rule is currently specified only in this
crate's source and in this evidence file. The controller should lift it into
`.plan/DIAGNOSTIC_ARCHITECTURE.md` §3.1's degenerate table, so `QM-0121` and
`QM-0122` inherit it as specification rather than re-deriving it.

### Ruling on deviation 2 — `reconstruction_not_finite`

**Correct deviation. Not blocking.**

§3.1's subnormal row carries the clause *"Never silently produce infinities"*.
That is a requirement on the **output**, and a normal-scale check demonstrably
does not deliver it. I verified the mechanism directly: for a constant unit at
`f32::MAX` under int8 symmetric the derived scale is `2.6793887e36`, which
`is_normal()` reports **true**, yet `127 · s` rounds past `f32::MAX`. So this is
a new refusal *kind* implementing an existing stated requirement, not a departure
from one.

I also verified the argument against a parameters-only bound, which is the part
that would have been easy to get wrong. Both cases such a bound would **wrongly
refuse** work correctly today:

* `constant_f32_max_int8_asymmetric` — reachable code is 0, reconstructs to
  `f32::MAX` bit-exactly;
* int4 at `-f32::MAX` — reachable code is 7, reconstructs bit-exactly;
* `s = f32::MAX` with ordinary inputs `[-1.0, 1.0]` — code 0, reconstructs to
  `[0.0, 0.0]` rather than overflowing.

The refusal names the unit, index, code and scale, and I confirmed no infinity
escapes into the caller's buffer. The crate is explicit that `out` is
unspecified on this one refusal because it can only be detected per value, and
that every other refusal precedes execution.

**Red-before-fix:** the evidence carries verbatim measured output for defect 1
(the seven-line probe table) and an honest note that the probe used `0.7071`
while the committed fixture uses `0.823457` because `clippy::approx_constant`
flags the former. Defect 2's failing state is described as measured but without a
verbatim capture. **I could not independently re-verify either red state**: the
branch is a single commit, so the pre-fix tree does not exist to run. What I did
verify is that the post-fix behaviour is correct, and that assertions which would
fail under the old rules are present and passing.

### The risk `QM-0122` inherits — adequately identified, not yet adequately placed

The hand-off itself is **correct and well-judged**. `## Not performed` names the

evidence file, under `## Not performed`. It is absent from `QM-0122`'s `TASK.md`

source would not encounter it. **Recommendation:** the controller should carry
this into `QM-0122`'s `TASK.md` §Risks, ideally together with lifting `s = |c|`
into §3.1 as specification. Non-blocking, and the underlying analysis is right.
