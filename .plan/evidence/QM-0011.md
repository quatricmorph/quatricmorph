### One behaviour the task's own text got wrong about this corpus, found by running it

`TASK.md` §Test Cases and `ARCHITECTURE.md` §6.2 describe `Att` as a four-way
ambiguity (Q, K, V, O). Over this corpus it is a **seven**-way one, because the
corpus carries the declared q/k/v projection *biases* alongside their weights and
an alias names a **role** — and a role covers more than one tensor. The first run
of the suite failed on exactly this (`left: 7, right: 4`), and the assertion was
corrected **toward what the repository produces**, not the other way round: the
test now pins all seven candidates in declared order, and additionally records
that even `Q[10]` is ambiguous here (weight and bias) and is answered with
candidates rather than an assumption that a user who types `Q` means the weight.
That is `NSIR-007` doing more work than the illustration suggested, not less.

### Two things checked before writing, that changed the design

1. **`architectures/conformance.json` cannot break plugin loading.**
   `Registry::load_dir` reads each directory entry and joins `plugin.toml`; a
   plain *file* at `architectures/conformance.json` yields
   `architectures/conformance.json/plugin.toml`, which `.is_file()` rejects. The
   pre-existing `q_architecture::tests::loading_from_the_repo_directory_matches_the_builtins`
   still passes, which is the check that this reasoning is right rather than
   merely plausible.
2. **`_`-prefixed metadata keys are the repository's existing convention** for
   provenance inside a JSON data file (`scripts/baseline.json`,
   `fixtures/tiny-qwen-single/golden.json`). The corpus follows it, so the
   top-level shape stays `{ "<family>": [rows] }` exactly as §Data Contracts
   specifies, and the loader treats a `_`-prefixed key as metadata rather than a
   family.

## Architecture conformance

**`ARCHITECTURE.md` §4.2 — the never-guess rule.** *"The resolver must be allowed
to return `unknown`. It must never guess a semantic role just because two tensors
share the same shape."* Asserted three ways: 60 negative rows stay `unknown`;
two identically shaped `[4096,4096]` tensors get different roles from their names
alone; and one name resolved under five different shapes (ranks 0–4) produces a
byte-identical record every time. The structural guarantee behind all three is
that `resolve_name` takes a `&str` — a shape is not merely unused, it is
unavailable — and `annotate`, the only entry point a shape can even reach, is
exercised as well so the guarantee is checked at the surface that has the field.

**`ARCHITECTURE.md` §4.2 — the record shape.** The §4.2 JSON
(`stack`, `layer`, `component`, `operation`, `parameter`, `axes`, plus `expert`
for MoE) is asserted field by field for every one of the 60 positive rows.

**`ARCHITECTURE.md` §6.1 — the canonical address.** Every positive row's address
was written by hand from the §6.1 form and is compared to what the resolver
emits. `every_corpus_row_resolves_identically_on_a_second_run` pins stability
across runs over all 120 rows, which is what makes the address safe to store in a
catalog, a report, or an annotation (`NSIR-004`).

**`ARCHITECTURE.md` §6.2 / `NSIR-007` — ambiguity.** *"If `Att` could refer to Q,
K, V, O … the query must return a list of candidates rather than silently picking
one tensor."* `an_ambiguous_alias_returns_candidates_rather_than_one_silent_pick_in_every_family`
asserts the full ordered candidate list for `Att[10]` in both alias-declaring
families, that `Q[10]` is *also* ambiguous over this corpus and is answered with
candidates, that `unique()` returns `AmbiguousAlias` naming them, that a
genuinely unique alias resolves to one, that a missing layer matches nothing with
confidence `0.0`, and that an undeclared alias is refused with an explanation.
`a_family_that_declares_no_aliases_rejects_every_alias_with_an_explanation` adds
the generic case, and `Router[5]` is shown resolving under `qwen` and being
**refused** under `llama` — one family's vocabulary never answers for another's.

**`ADR-010` — rank > 3 refuses rather than flattens.** Rank is not expressible in
a *name* resolver; nothing here sees a shape. The nearest expressible surface is
the number of axis labels, so `no_corpus_row_declares_more_axes_than_the_implemented_rank_ceiling`
guards the corpus (60 rows) as the companion to the pre-existing
`q_architecture::tests::no_plugin_rule_declares_more_axes_than_the_implemented_rank_ceiling`,
which guards the manifests. Stated as a limit rather than as a claim that rank is
handled here.

**Exact / sampled / approximate.** Resolution is **exact**: a deterministic
function of a raw name and a declared rule table, nothing sampled and nothing
estimated. The corpus carries `"_fidelity": "exact"` and
`the_corpus_declares_exact_fidelity_because_resolution_samples_and_estimates_nothing`
asserts it, so the label cannot be silently dropped.

**`ARCHITECTURE.md` §19 — a pattern is not a concept.** The corpus carries a
`_what_this_corpus_is_not` field saying so, and the suite's module documentation
repeats it: `query_projection` is the checkpoint author's word propagated through
a declared rule table, not a finding about any weight.

**`.plan/TEST_STRATEGY.md` §0.** All three properties preserved: no test touches
the network; expected values are hand-written or come from a checked-in golden,
never from the code under test; test names are assertions.

### Which tests would pass vacuously — the explicit statement this record owes

`QM-0010` volunteered that two of its tests passed against an **empty** rule
table, because an empty table answers `unknown` to everything. Every test here was
checked against that standard, and the answer is stated per test rather than in
aggregate:

* **Would a negative row pass against an empty rule table?** On its own, yes —
  which is why **no negative row stands on its own**. Each of the 52 negative
  rows in the three implemented families names a `control`: a positive row of the
  same family that must *still resolve*. `an_empty_rule_table_fails_this_suite_rather_than_satisfying_its_negative_rows`
  clears every rule from `generic`, `llama` and `qwen` in turn and asserts not
  only that the corpus rejects the result but that it rejects it **through the
  controls** (`failures.iter().any(|f| f.contains("the control"))`). Mutation
  `m05` shows the same mechanism firing on a single deleted pattern.

* **The eight `kimi` and `deepseek` rows ARE vacuous in isolation, and this is
  the one place in the suite where that is true.** They would be satisfied by an
  empty rule table — because that is exactly what those plugins have, and
  asserting it is the entire point. They therefore carry no control, and the
  corpus says so in the row text. What makes the pair non-vacuous is the second
  half of `an_unimplemented_family_never_claims_a_model_and_the_generic_fallback_answers_instead`:
  the same raw name that `kimi` refuses is shown **resolving** through the
  `generic` plugin the registry selects in its place, so the rows cannot be
  passing merely because resolution is broken. Mutation `m12`
  (`implemented = false` → `true`) shows the test failing.

* **Would any test pass over an empty *corpus*?** Nine could have, and each was
  given an explicit count guard so it cannot:
  `every_corpus_row_resolves_exactly_as_the_corpus_says_it_must` (≥ 100 rows),
  `every_corpus_row_resolves_identically_on_a_second_run` (≥ 100),
  `no_family_lists_the_same_raw_name_twice` (≥ 100),
  `every_declared_pattern_of_every_family_is_exercised_by_at_least_one_corpus_row`
  (≥ 54 patterns), `no_corpus_row_declares_more_axes_than_the_implemented_rank_ceiling`
  (≥ 54 rows with axes), `an_untaught_name_stays_unknown_and_is_never_answered_with_a_nearest_guess`
  (≥ 30 negatives), `the_llama_and_qwen_corpora_agree_on_every_raw_name_they_share`
  (≥ 40 shared), `the_corpus_agrees_with_the_checked_in_qwen_fixture_golden_on_every_shared_raw_name`
  (≥ 21 compared), `a_named_architecture_outranks_the_generic_fallback_and_is_selected_for_every_key_it_declares`
  (≥ 9 keys). Mutation `m19` truncates every family to one row and turns 14 of
  the 28 tests red, which is the check that those guards fire.

* **One test's claim cannot be falsified by any data mutation, and this is said
  rather than glossed.** `every_corpus_row_resolves_identically_on_a_second_run`
  asserts determinism of a pure function; no corpus or manifest edit can make
  resolution nondeterministic. It is a regression guard against a future change,
  not a discriminating test today. Its count guard is what stops it from passing
  over an empty corpus (mutation `m19`). It is reported here as the weakest test
  in the suite.

* **Two tests are detector self-tests** —
  `a_corpus_family_the_registry_does_not_carry_is_named_in_the_failure` and

Verified by attack rather than by reading the claim. The reviewer stripped **all
52 `control` fields** from `architectures/conformance.json` and ran
`an_empty_rule_table_fails_this_suite_rather_than_satisfying_its_negative_rows`.
It went **red**, with exactly the right complaint:

```
an empty `generic` rule table must break the negative rows' controls,
not merely the positive rows:
  generic: `model.embed_tokens.weight` did not resolve; the corpus expects ...
```

That is the decisive result: the test is **not** satisfied by positive-row
failures alone — it requires the breakage to arrive *through the controls*. The
substring guard `failures.iter().any(|f| f.contains("the control"))` cannot be
spoofed by any other failure message in `conformance_failures`, since the only
strings containing `the control` are emitted by the anti-vacuity branch and by
the pairing assertion, and tensor names carry no spaces.

The pairing is real, not nominal: every negative row's control is its nearest
positive twin — `q_proj_v2.weight` → `q_proj.weight`, `o_proj.bias` →
`q_proj.bias`, `experts.abc.up_proj` → `experts.37.up_proj` — so a control
isolates the specific rule its negative row is a near-miss of, rather than being
satisfied by some unrelated name elsewhere in the family. `m05` demonstrates
this directly: deleting one Qwen pattern made four separate negative rows report
their controls dead.

**The `kimi`/`deepseek` disclosure is honest and complete.** Exactly 8 rows carry
`canonical: null` with no control (kimi 4, deepseek 4), and the corpus itself says
so in each row's `why`. No other family has an uncontrolled negative row —
generic 15/15, llama 18/18, qwen 19/19 all carry controls, and
`every_negative_row_of_an_implemented_family_names_a_control_that_still_resolves`
panics if one does not. Their non-vacuity is genuinely carried elsewhere:
`an_unimplemented_family_never_claims_a_model_and_the_generic_fallback_answers_instead`
shows `model.layers.10.self_attn.q_proj.weight` — a name kimi refuses — resolving
through `generic` to `model.layers[10].self_attention.query_projection.weight`,
so the rows cannot be passing because resolution is broken. "Eight rows are
vacuous and no test is" is accurate as stated.

**On the nominated weakest test.** The implementer's self-assessment of
`every_corpus_row_resolves_identically_on_a_second_run` is correct and is the
right call to have volunteered: it asserts determinism of a pure function, and no
corpus or manifest mutation can falsify it. It is accepted as-is. It is a
forward-looking regression guard (it would catch iteration-order or cached state
introduced later), its `compared >= 100` guard stops it passing over an empty
corpus, and `m19` fires it. Strengthening it — resolving through two independently
built `Registry::builtin()` instances rather than one — is offered as a
**suggestion, not a change request**.
