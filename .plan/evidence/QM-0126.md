## 4. The kernel on device

### 4.1 Documented reduction order

The authoritative statement is the header of
`gpu/metal/paired_reduction.metal`. It is fixed, it contains **no atomics**,
and it is:

1. **One threadgroup per channel.** Threadgroup `g` touches only channel `g`'s
   elements; channels never interact and nothing accumulates across
   threadgroups.
2. Within a threadgroup, exactly **256 threads**. Thread `t` visits its
   channel's elements at positions `t, t+256, t+512, …` in strictly increasing
   order, into private registers.
3. A **fixed binary tree** over the 256 lanes:
   `for (stride = 128; stride > 0; stride >>= 1) lane[t] += lane[t + stride]`,
   with a threadgroup barrier between levels. Lane 0 holds the result.

Steps 2 and 3 depend on the threadgroup size, so the host dispatches with
`dispatchThreadgroups:threadsPerThreadgroup:` and never `dispatchThreads:`,
which would let the driver reshape the final threadgroup and change the tree.
A device whose `maxTotalThreadsPerThreadgroup` is below 256 is **refused**, not
silently shrunk. (The M3 Pro reports 1024.)

**Accumulation strategy, stated as `QM-0127`'s tolerance must be set against
it:** Metal has no double precision. Accumulation is **`f32` on device**, and
the delta is formed as `f32(base) − f32(counterpart)`, whereas `CpuBackend`
widens both operands to `f64` and subtracts there. That difference — not the
reduction order — is the dominant divergence from the reference. The host
widens each channel's five `f32` outputs to `f64` on readback: a **widening**,
not a re-accumulation.

**Segmentation, for `QM-0127`:** one kernel serves three cases through four
stride parameters.

| pass | `channel_count` | `elements_per_channel` | `element_stride` | `channel_stride` |
| --- | --- | --- | --- | --- |
| `ChannelAxis::Rows` | rows | columns | 1 | columns |
| `ChannelAxis::Columns` | columns | rows | columns | 1 |
| whole block | 1 | rows × columns | 1 | 0 |

The whole-block partials come from that **second, independent dispatch** — a
single channel spanning the whole block, *enumerated* in flat row-major order
and *reduced* in the same stripe-and-tree order as every other pass — not from
re-summing the per-channel results. That keeps them identical whichever
axis was requested — the property `crates/q-gpu/src/paired.rs` names
`the_whole_block_partials_are_bit_identical_whichever_axis_is_requested`, which
a per-channel fold would have quietly broken (the two groupings associate the
additions differently). `a_small_paired_reduction_runs_on_device_and_returns_
the_right_shape` asserts the Rows and Columns whole-block fields are equal with
`==`, no tolerance.

### 4.2 A small paired reduction's actual device output

Input is the QM-0121 hand fixture, a 3×4 pair whose every value is a multiple
of ¼. Printed by
`a_small_paired_reduction_runs_on_device_and_returns_the_right_shape`.

```text
QM-0126 device output, ChannelAxis::Rows: PairedPartials {
    count: 12,
    sum_sq_base: 79.6875,
    sum_sq_delta: 3.25,
    sum_abs_delta: 5.5,
    max_abs_delta: 1.0,
    max_abs_base: 4.5,
    per_channel: [
        ChannelPartials { count: 4, sum_sq_base: 30.0,    sum_sq_delta: 1.5,    sum_abs_delta: 2.0,  max_abs_delta: 1.0,  max_abs_base: 4.0  },
        ChannelPartials { count: 4, sum_sq_base: 29.0,    sum_sq_delta: 0.8125, sum_abs_delta: 1.75, max_abs_delta: 0.5,  max_abs_base: 4.5  },
        ChannelPartials { count: 4, sum_sq_base: 20.6875, sum_sq_delta: 0.9375, sum_abs_delta: 1.75, max_abs_delta: 0.75, max_abs_base: 3.75 },
    ],
}
```

`ChannelAxis::Columns` on the same pair returns 4 channels of `count: 3` and
the identical whole-block fields.

**An observation, not a verification.** The same test printed `CpuBackend`'s
result for the same input beside it and the two are equal in every field. That
is worth recording and it is *not* a verification claim: this fixture was
chosen because every value is a multiple of ¼, so every square is a multiple of
1/16 and each sum is exact in binary floating point — the f32/f64 difference
described in §4.1 has nothing to bite on. One agreeing fixture is not a
tolerance and is not a proof. Establishing agreement over inputs that are *not*
exactly representable is `QM-0127`, and it is explicitly out of scope here; no
test in this task compares the two backends.

### 4.3 Determinism

`repeated_dispatches_of_the_same_block_return_identical_bytes` runs a 7×300
pair five times and asserts full `PairedPartials` equality. 300 columns exceeds
the 256-lane threadgroup, so each thread's stripe holds more than one element
and the tree reduction is genuinely exercised rather than degenerate. `V1-13`.

## 5. Staging budget

```text
device staging = base block bytes + counterpart block bytes ≤ 256 MiB
```

Enforced in `MetalBackend::check_workload` via
`Workload::for_paired_blocks(rows, columns)`, which already multiplies by 2.
The refusal is `QError::BudgetExceeded { budget_name: "metal_device_staging", … }`
— named for the budget that actually applies, rather than `device_memory`,
which would suggest the M3 Pro's 30 GB.

`the_staging_budget_counts_both_blocks_of_the_pair_without_a_device` is the
discriminating case:

| pair | bytes for **one** block | bytes for the **pair** | outcome |
| --- | --- | --- | --- |
| 4096 × 8192 | 128 MiB | 256 MiB | accepted, exactly at the budget |
| 4096 × 8193 | 128 MiB + 16 KiB | 256 MiB + 32 KiB | **refused** |

The second row fits comfortably if only one block is counted. If the doubling
were ever dropped, that assertion is what fails.

`the_budget_refusal_precedes_any_dispatch` builds a backend with a 16-byte
declared budget and asserts the 3×4 pair is refused with `BudgetExceeded`
naming `metal_device_staging` — before any buffer exists, let alone a dispatch.

Refusal order mirrors `CpuBackend::reduce_paired_blocks` exactly: shape,
emptiness, staging budget, raggedness, finiteness, and only then the device.
`crates/q-gpu/src/paired.rs`'s `validate_pair`, `require_dense` and
`require_finite` were widened from private to `pub(crate)` and are **shared**,
not re-implemented — a second copy would drift from the reference it exists to
match.

## 7. Not performed

Stated plainly, because the repository's credibility rests on it.

* **Numerical verification against `CpuBackend` was not performed.** No
  tolerance was established, no differential test was written, and none should
  be read into §4.2's observed agreement on one exactly-representable fixture.
  That is `QM-0127`, and `hardware_verified` stays `false` until it passes.
* **The no-device skip path did not execute here.** This machine has an M3 Pro,
  so `device_or_skip` took the `Some(_)` branch in every run. The skip branch is
  compiled and prints a named reason
  (*"no Metal device on this machine (MTLCreateSystemDefaultDevice returned
  nil)"*), but it has not been observed firing on hardware that lacks a GPU.
  What *was* exercised in place of it is the deviceless path that does not need
  absent hardware: `MetalBackend::with_declared_staging_budget` runs the whole
  refusal ladder — budget, shape, finiteness, and a dispatch refusal — with no
  device queried, in four tests.
* **A build with the `metal` feature on and the toolchain absent was not
  performed.** The failure path in `build.rs` panics naming the file; it was
  read, not run, because uninstalling Xcode was not on the table. Note this is
  a *different* condition from a missing device: a toolchain missing while the
  feature is explicitly on is a build error by design; a missing device at run
  time is `None`.
* **`block_statistics`, `matmul`, and any histogram on Metal do not exist.**
  They return `QError::NotImplemented { requirement: "GPU-003", … }` pointing
  at `CpuBackend`, and `capabilities()` reports `supports_* = false` so no
  scheduler routes work to them.
* **No non-macOS target was built with the feature on.** `build.rs` panics with
  a named message for `target_os != "macos"`; that message was read, not
  triggered.
* **No performance claim.** Nothing here was benchmarked. `QM-0126` asked for a
  straightforward correct kernel and optimisation is explicitly out of scope;
  the 14-core M3 Pro figure above is an identity, not a throughput.

## 8. Deviations from the task plan

* **`gpu/metal/qm_metal_shim.m` is not in `Files Expected to Add`.** The task
  anticipated `crates/q-gpu/src/metal.rs`, `gpu/metal/paired_reduction.metal`
  and `crates/q-gpu/build.rs`; all three exist. The shim is additional because
  the Metal API is Objective-C only, and the alternative — a crates.io binding
  such as `metal-rs` — would have added packages to `Cargo.lock` for every
  consumer of this workspace whether or not they enable the feature, and put an
  unaudited transitive tree in front of `scripts/license-audit.sh`. ~230 lines
  of Objective-C against Apple's own SDK leaves `Cargo.lock` byte-identical. It
  sits inside the task's stated program boundary (`gpu/metal/`).
* **`ComputeCapabilities` gained no fields.** The task's Data Contracts asks it
  to report unified-memory size and maximum buffer length, and also says "no new
  public types". Adding fields would change the serde shape for every backend
  and for `q-report`'s manifest. Instead `MetalBackend::device()` returns a
  `MetalDeviceInfo` carrying every queried figure, and `display_name` names the
  device. The numbers are reported; the shared struct is unchanged.
* **`crates/q-gpu/src/paired.rs` was edited**, beyond the two files the task
  listed: three validators became `pub(crate)` so the Metal path shares the
  reference's refusal logic instead of copying it. No behaviour changed.
* **`gpu/metal/compute.metal` and `gpu/wgsl/compute.wgsl` were left alone.**
  Both remain placeholders, as the task requires.
