## Summary

`crates/q-gpu/src/paired.rs` (new) holds `ChannelAxis`, `ChannelPartials`,
`PairedPartials` and the CPU reference reduction. `crates/q-gpu/src/lib.rs` gains
the trait method with a **refusing default** (so `q_cuda::CudaBackend` compiles
untouched), `CpuBackend`'s implementation, and `Workload::for_paired_blocks`,
which charges the budget for **both** operands.

The kernel is one pass in fixed row-major order with `f64` accumulators over
`f32` inputs, preceded by five refusals that all complete before any arithmetic.
It allocates exactly one `Vec<ChannelPartials>` — `channels × 48 B` — and nothing
proportional to the element count.

Three design decisions worth a reviewer's attention:

1. **The whole-block fields are accumulated separately, in row-major element
   order, and never by re-summing `per_channel`.** That makes them
   *axis-invariant*: `paired_block_reduction(.., Rows)` and `(.., Columns)`
   produce bit-identical whole-block figures. Since
   `.plan/DIAGNOSTIC_ARCHITECTURE.md` §4.2 builds the tensor-level RMSE out of
   exactly these fields, the alternative would have made a tensor's reported
   error depend on which channel axis a caller happened to ask for. The cost is
   that `Σ per_channel` may differ from the whole-block field in the last ulp
   when the sums are inexact; this is **documented on the type** and is asserted
   in both directions by tests, so `QM-0122`/`QM-0123` cannot trip over it
   silently.
2. **The finiteness scan is a separate pass**, not a check inside the
   accumulation loop, so "refuses before arithmetic" is a structural property
   rather than an argument about which partial results a caller can observe.
3. **`PairedPartials` has no `merge`.** Composition is an acceptance criterion,
   and a test that called the implementation's own merge would prove nothing
   about composability. The merge arithmetic is written out in the test, and
   aggregation stays `QM-0123`'s.

### Criterion 1 — the hand computation, written out

```text
base                              counterpart                    delta = base - counterpart
 1.00  -2.00   3.00  -4.00         1.50  -1.00   3.00  -3.50      -0.50  -1.00   0.00  -0.50
 0.50   1.50  -2.50   4.50         0.25   2.00  -2.00   4.00       0.25  -0.50  -0.50   0.50
-1.25   2.25   0.00   3.75        -1.00   2.50   0.50   3.00      -0.25  -0.25  -0.50   0.75
```

Every value is a multiple of ¼, so every square is a multiple of ¹⁄₁₆ and every
sum is **exact** in binary floating point. The expectations are compared with
`==`, with no tolerance to hide behind.

```text
whole block   count 12
              sum_sq_base   = 30 + 29 + 20.6875            = 79.6875
              sum_sq_delta  = 1.5 + 0.8125 + 0.9375        =  3.25
              sum_abs_delta = 2 + 1.75 + 1.75              =  5.5
              max_abs_delta = 1.0   (row 0, column 1)
              max_abs_base  = 4.5   (row 1, column 3)

axis = Rows          count  sum_sq_base  sum_sq_delta  sum_abs_delta  max_abs_delta  max_abs_base
  row 0                 4      30.0          1.5           2.0            1.0            4.0
  row 1                 4      29.0          0.8125        1.75           0.5            4.5
  row 2                 4      20.6875       0.9375        1.75           0.75           3.75

axis = Columns       count  sum_sq_base  sum_sq_delta  sum_abs_delta  max_abs_delta  max_abs_base
  column 0              3       2.8125       0.375         1.0            0.5            1.25
  column 1              3      11.3125       1.3125        1.75           1.0            2.25
  column 2              3      15.25         0.5           1.0            0.5            3.0
  column 3              3      50.3125       1.0625        1.75           0.75           4.5
```

Each term is written out in the test's own comments, and the per-row / per-column
figures sum back to the whole-block figures — asserted by
`the_whole_block_partials_equal_the_sum_of_the_per_channel_partials`, which runs
only on this exact fixture and says in its own comment why it may not run on an
inexact one.

**Provenance of these numbers.** They were derived independently of the Rust
under test, in exact rational arithmetic (`fractions.Fraction`, not floating
point) in a scratch script, then written into the test as literals with the
term-by-term derivation beside them. No expected value in any test was produced
by `q_gpu::CpuBackend`.

### The ragged-block defect, found by the concurrent agent

While this task was in progress the second agent (see *Claim limits*) added a
`require_dense` guard directly into `crates/q-gpu/src/paired.rs` in the shared
worktree. It identifies a real hole in the implementation as first written:
`BlockData::new` rejects a ragged block, but `rows`, `columns` and `values` are
all `pub`, so a block whose declared shape outruns its buffer reaches this kernel
from safe code, clears every other refusal, and **panics** in the accumulation
loop.

This was not taken on trust. The 36-line guard was read in full, and the defect
it prevents was reproduced by removing the two guard calls and re-running:

```text
thread 'paired::tests::a_block_whose_buffer_is_shorter_than_its_shape_is_refused_not_panicked_on'
panicked at crates/q-gpu/src/paired.rs:320:36:
index out of bounds: the len is 1 but the index is 1
```

The guard is therefore load-bearing, not decorative. It is kept, and the test
`a_block_whose_buffer_is_shorter_than_its_shape_is_refused_not_panicked_on` was
written **by this agent** to cover it — a short buffer, a long buffer, an
overflowing declared shape, and both operands. The commit body records the
provenance. A panic is not a refusal: it carries no requirement ID and cannot be
returned to a caller that was handed a `Result`.

## Architecture conformance

**Governing sections**

* `.plan/DIAGNOSTIC_ARCHITECTURE.md` §4.1 — the trait signature and the
  `PairedPartials` field list are implemented exactly as written, including the
  comment semantics (`Σ w²` as the *denominator*, `‖·‖_F²` *before* the root).
* §4.1 "everything is a partial, nothing is a final metric" — no RMSE, no
  relative error, no norm appears in either struct, and the type documentation
  says why adding one would be a defect. `V1-12`'s failure mode is documented at
  the point where someone would be tempted to introduce it.
* §4.2 — fixed reduction order, single-threaded accumulation, `V1-13`
  byte-identical output. Row-major, no parallelism, and no `rayon`-shaped
  invitation to add any.
* §4.3 — `CpuBackend` is the numerical ground truth. **No GPU executed anything.**
  No Metal or CUDA path was added; `QM-0126` owns the Metal lane and the CUDA
  lane is `Deferred`.
* §5 — the pair is charged against the residency budget as two blocks, not one
  (`Workload::for_paired_blocks`). Both inputs are borrowed, never copied.
* §3.2 — the axis convention is asserted by a non-square, non-symmetric fixture,
  and transposing it changes the answer (`V1-11`).
* `ARCHITECTURE.md` §12.3 — this is the compute side of the split; nothing here
  renders.

**Binding ADRs**

* **ADR-010 (rank ceiling).** `ChannelAxis::from_index(axis, rank)` refuses rank
  > 3 with `QError::NotImplemented { requirement: "GRID-007", .. }`, naming
  ADR-010 and the ceiling — *refusing rather than flattening*, which is the
  ADR's central claim. Rank 0, 1 and 3 refuse with the same message
  `BlockExtent::clamped_to` already gives for a non-rank-2 shape, rather than a
  second, competing rule; the doc comment states that rank 3 is within the
  ADR's ceiling for axis *binding* but that a block is a 2-D slice until
  `QM-0040` adds the depth extent.
* ADR-009 world axes — not touched; nothing here binds display axes.

**`ARCHITECTURE.md` §19 checks**

| §19 rule | Status |
| --- | --- |
| No cube-per-weight GLBs | Not applicable; nothing here emits geometry |
| No absolute positions per scalar | Not applicable |
| No whole tensor into the browser | Honoured — the output is `channels × 48 B` of partials, never values |
| Cesium is not a compute engine | Honoured; this is the compute crate |
| Chat may not execute terabyte expressions unplanned | Honoured — `check_workload` refuses an oversized pair up front |
| No semantic claim about weights | Honoured — the module claims arithmetic and nothing else |

**`AGENTS.md` rule 4 — exact/sampled/approximate.** Every figure this task
produces is **exact**: an `f64` accumulation over the full block with no
sampling and no approximation. `ComputeCapabilities`/`TensorStatistics` already
carry the `approximate` flag for surfaces that need it; `PairedPartials` has no
such flag because there is no code path here that could set it.
