### A defect in the task's Data Contracts, resolved rather than papered over

`TASK.md:90-93` specifies `StreamedBlock { … pub data: BlockData … }`, and
`TASK.md:30` cites `crates/q-gpu/src/lib.rs:105` as `BlockData`'s home. That is
**unsatisfiable as literally written**: `crates/q-gpu/Cargo.toml` declares
`q-tensor-runtime = { workspace = true }`, and `crates/q-gpu/src/lib.rs:38` uses
`q_tensor_runtime::{BlockExtent, TensorBlock}`. A `q-tensor-runtime` module that
imported `q_gpu::BlockData` would close a dependency cycle and Cargo would refuse
to build the workspace.

Resolved by **moving the type to `q-tensor-runtime` and re-exporting it from
`q-gpu`**:

```rust
// crates/q-gpu/src/lib.rs
pub use q_tensor_runtime::BlockData;
```

That is one line outside the stated program boundary, and it was the *only* line
needed: `q-cuda` (`q_gpu::BlockData`), `q-gpu`'s own `CpuBackend`, and the
`tests/` crate all resolve through the re-export unchanged. Verified by
`cargo build --workspace --all-targets` and
`cargo clippy --workspace --all-targets -- -D warnings`, both exit 0. The
alternative — a second container type declared inside `stream.rs` — was rejected
because two types named `BlockData` in one workspace is worse than one line of
re-export, and because it would force a conversion shim on `QM-0031`, `QM-0035`
and `QM-0041`. The direction is also the correct one: `BlockData` is the value
container the block *runtime* produces, not a GPU concept.

## Summary

`crates/q-tensor-runtime/src/stream.rs` adds `BlockStream`: a pull-based iterator
over a tensor's block grid that range-reads each block through a
`q_source::ModelSource`, decodes it into a `BlockData`, and emits a
`StreamedBlock`. `crates/q-source/src/budget.rs` gains the five named budgets
`.plan/MEMORY_BUDGET.md` §4–§5 defines.

**The measured residency result.** Peak *heap* allocation while streaming, with a
counting `#[global_allocator]`, is **268,355 bytes — bit-identical at 1024²,
2048², and 4096², and identical again for 16 blocks of a 65536² tensor whose
payload would be 16 GiB.** That is one decoded 256×256 f32 block (262,144 B) plus
one 1 KiB run buffer plus 5,187 B of bookkeeping. The declared ceiling is 2 MiB;
the measurement is 7.8× under it. Under the bounded output queue with a stalled
consumer the peak is **1,580,715 B**, which is exactly `(capacity + 2) × 262,144`
— the documented worst case, not a surprise.

**Do not read this as gate G1.** See *Claim limits*.

Three findings worth a reviewer's attention:

1. **Dtypes that cannot widen into `f32` exactly are refused, not rounded.**
   `BlockData` is `f32` by construction and `f32` carries 24 significand bits, so
   `I32`/`U32`/`I64`/`U64`/`F64` values above 2²⁴ would be silently wrong.
   `BlockStream` returns `UnsupportedDType` for those five rather than emitting an
   approximation labelled exact. `TASK.md` does not ask for this; refusing is the
   only answer consistent with `SRC-014` and ADR-010, and it is reversible.
2. **`MAX_OUTPUT_QUEUE_DEPTH` cannot be the queue bound in this task.** 64 decoded
   256×256 blocks is 16 MiB, which would break acceptance criterion 2 outright.
   `.plan/CUDA_ARCHITECTURE.md` sizes that depth for *compact* per-block output
   (statistics records), not decoded blocks. The queue capacity is therefore
   `min(max_output_queue_depth, max_concurrent_blocks)`, documented in
   `BlockStream::queue_capacity`. When `QM-0031` puts compact results on the queue,
   the depth ceiling becomes the binding one.
3. **Adaptive halving is resolved at construction, before the grid exists.**
   Halving mid-stream would change the block grid under a consumer and break both
   acceptance criterion 8 and resume. A per-block allocation failure *after*
   construction is an error naming the budget, never a silent regrid.

Three of my own mistakes are recorded below rather than quietly fixed. Two were
caught **by the tests**: a `requested_config` that reported the post-halving block
size, and a backpressure bound written as `capacity + 1` when the real bound is
`capacity + 2`. The third was caught **by review, not by any test** — the
bounded-queue phase's stall was arranged so that it would fail on a *slow*
machine, i.e. exactly on a loaded CI runner. It is now front-loaded and verified
under a genuinely oversubscribed machine. A fourth, an arithmetic slip in a
hand-computed bf16 expectation, is under *Validation evidence*.

### Two bugs the tests caught, not review

**(a) `requested_config()` reported the post-halving block size.** First real run:

```
---- stream::tests::allocation_failure_halves_the_block_and_completes stdout ----
thread '...' panicked at crates/q-tensor-runtime/src/stream.rs:1615:9:
assertion `left == right` failed: the requested size is still reportable
  left: (128, 128)
 right: (256, 256)
```

Cause: `let (config, halvings) = Self::resolve_block_size(config, …)` shadowed the
requested config, so `requested: config` stored the resolved one. Fixed by binding
the resolved value to `effective`. Without this, a consumer could not report that
halving had occurred — which is the only way a smaller-than-expected block count
is explicable.

**(b) The backpressure bound was written as `capacity + 1`; the real bound is
`capacity + 2`.** Caught by `./scripts/verify-baseline.sh`, not by the per-crate
run:

```
---- stream::tests::a_full_output_queue_blocks_the_reader_instead_of_growing stdout ----
thread '...' panicked at crates/q-tensor-runtime/src/stream.rs:1534:9:
queue high water 3 exceeded capacity 1 + 1
```

Cause, and why `+ 2` is the honest bound rather than a loosened one: the producer
increments the in-flight counter before `send` and the consumer decrements after
`recv` returns, so a consumer descheduled between `recv` and its decrement is a
third live block — `capacity` buffered + 1 in the reader's hand while `send`
blocks + 1 in the sink's hand. `drive_bounded`'s own doc comment and
`StreamOutcome::queue_high_water`'s already said `capacity + 2`; the assertion
disagreed with the design and was wrong. The measured bounded-queue peak
independently confirms it: **1,580,715 B ÷ 262,144 = 6.03 blocks = capacity 4 + 2**.

The load-bearing assertion — `high_water < total`, i.e. the queue does not grow
without bound — was never relaxed, and a staging-budget assertion was **added**
alongside the corrected bound.

### (c) A load-sensitive test setup, corrected before it could flake in CI

The bounded-queue phase of `bounded_residency.rs` first stalled its consumer with
a **25 ms sleep per block**, and asserted `queue_high_water > 1` so the phase could
not silently stop measuring the worst case. That assertion is sound; the setup was
not. It only holds if the reader can produce a second block inside one consumer
sleep — the reader takes ~8 ms per 256×256 block in a debug build — so a **slow**
machine makes it fail. That is precisely a loaded CI runner, and `QM-0101` and
`QM-0120`–`QM-0125` all run `cargo test --workspace` against a floor that now
contains this test.

The stall is now **front-loaded**: one 200 ms sleep on the first block, none after.
The reader queues all `capacity` blocks and parks in `send` within ~32 ms, so the
margin is ~6× instead of ~3×, and the phase costs 200 ms rather than 400 ms.

Nothing was loosened: `<= capacity + 2`, `< total`, `> 1`, and the staging-budget
assertion all remain, and the phase still measures the same six live blocks —
verified by the reported numbers being unchanged:

Why the ceiling is not a number chosen after the fact: `.plan/MEMORY_BUDGET.md` §4
predicts `N × E × 4 = 1 MiB`, and `TASK.md` acceptance criterion 2 states 2 MiB.
Both predate the measurement.

Why the *synthetic* source and not a file: `LocalFsSource` is `mmap`-backed and a
memory map never reaches `GlobalAlloc`, so on a mapped file this allocator could
not distinguish "streamed one block at a time" from "mapped the whole file and
copied one block at a time". The synthetic source hands every window over as a
heap `Vec`, so every byte the streamer receives is counted. The mapped path is
covered for correctness by `real_fixture_blocks.rs`.

The heap number is necessary but not sufficient on its own, so `bytes_read` is
asserted independently on every block in every phase:
`block.bytes_read == block.extent.element_count() × dtype_width`, and
`run_count == extent.rows()`. That catches over-reading, which no allocator
number can.

### The central claim — bounded residency — reproduced, and its method audited

Reproduced **byte-identically** on my own run of
`cargo test -p q-tensor-runtime --test bounded_residency -- --nocapture` (exit 0):

```text
PERF-001 (exact, counting allocator): peak allocation 1024² 268355 B / 2048² 268355 B
/ 4096² 268355 B; 16 blocks of a 65536² (16 GiB) tensor 268355 B; bounded-queue 1024²
with a stalled consumer 1580715 B (queue high water 5 of capacity 4); ceiling 2097152 B
```

Spread across the three sizes is **0 B** against a 64 KiB tolerance, and 268,355 B
is **7.8× under** the declared 2,097,152 B ceiling. The bounded-queue figure is
`1,580,715 ÷ 262,144 = 6.03` blocks = `capacity 4 + 2`, i.e. the documented worst
case rather than a surprise.

**Why the method is sound, and where it is not what it says:**

1. **The allocator does observe the streaming path.** `SyntheticShard::read_range`
   hands each window over as `vec![0u8; length]`
   (`tests/bounded_residency.rs:168`), so every byte the streamer receives passes
   through `GlobalAlloc`. The streamer's own two buffers — the decoded
   `Vec<f32>` (`src/stream.rs:658`) and the single reusable run `scratch`
   (`src/stream.rs:671-673`) — are heap allocations. Nothing on this path bypasses
   the counter. `268,355 = 262,144` (one decoded 256×256 f32 block) `+ 1,024` (one
   1 KiB run buffer) `+ 5,187` reconciles exactly.
2. **The mmap caveat does not apply to the phase that establishes AC2.** The
   implementer is right that maps never reach `GlobalAlloc` — but the three-size
   phase runs against the heap-backed synthetic source, not `LocalFsSource`, so
   AC2's number stands on its own instrument. The mmap path is covered separately
   by `tests/real_fixture_blocks.rs`.
3. **AC2's measurement is single-threaded** (`drive`, not `drive_bounded` —
   `tests/bounded_residency.rs:231`), so the counting allocator's `Relaxed`
   `fetch_max` cannot race in that phase. Checked deliberately, and it resolves in
   the implementer's favour.
4. **`measure()` is honest**: it rebases `PEAK` to current `LIVE` and subtracts,
   so it reports residency the body *adds* rather than a process high-water mark.
5. **One finding — the evidence overstates its own method. See *Findings* below.**
6. **The 4096² and 65536² tensors are synthetic descriptors, not files, and the
   evidence says so plainly** (*Claim limits*, and the module header of
   `tests/bounded_residency.rs`). Nothing reads as though 16 GiB was streamed:
   the wording is consistently "a 65536² tensor **whose payload would be** 16 GiB"
   and "16 blocks **of** it". A synthetic descriptor is the right instrument —
   it proves the code does not materialise — and the largest real artifact
   actually read is correctly stated as the 352,824,413-byte checkpoint, four
   blocks of it.

### Ruling — the `BlockData` out-of-boundary edit: a plan defect, correctly handled

### Ruling — refusing `I32`/`U32`/`I64`/`U64`/`F64`: correct, and breaks nothing

This is the implementer's own judgement, absent from `TASK.md`. I judged it
independently:

* `BlockData.values` is `Vec<f32>`; `f32` carries 24 significand bits, so any of
  those five dtypes can hold values `> 2²⁴` that would be **silently rounded**
  and then presented as exact. That is the failure class ADR-010 rejects for rank
  ("a confidently wrong picture") and `SRC-014` rejects for unknown dtypes.
* **No documented requirement is broken.** `TASK.md`'s `## Error Handling` says
  only "Unknown dtype → refused, never guessed"; its `## Test Cases` name f32,
  bf16 and f16 exclusively; AC4 and AC9 name f32/bf16/f16. Nothing in `TASK.md`,
  `MEMORY_BUDGET.md` §4, `PERFORMANCE_PLAN.md` §2.2 or ADR-010 requires an
  integer or f64 tensor to stream.
* **Nothing is rounded into `f32` silently.** I read `decode_element`
  (`src/stream.rs:319-355`): `F32` goes through `f32::from_le_bytes`, `BF16`/`F16`
  through the audited bit-pattern decoders — **no `f64` round trip on the float
  paths**. Only `Bool`/`U8`/`I8`/`I16`/`U16` use `decode_scalar(..) as f32`, and
  every value of those is `≤ 65535 < 2²⁴`, so the narrowing is provably exact.
  The refusal fires at construction (`src/stream.rs:427-435`), before any read.
* The refusal is `QError::UnsupportedDType`, matching the existing idiom, and it
  is reversible: widening later needs a wider `BlockData`, not a redesign.

**Ruling: correct, and the right instinct. Refusing beats lossily widening.**
