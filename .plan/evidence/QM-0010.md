### What the repository already decided

Reading before writing changed the shape of this task substantially. Four
findings, each with a citation:

1. **`TensorRole` already carries `AttentionQueryNorm` and `AttentionKeyNorm`**
   (`crates/q-source/src/role.rs:47-48`, `as_str` at `:77-78`, `parse` at
   `:105-106`, `component()` at `:139-140`). `TASK.md` §Implementation Plan step
   4 says "Add `q_norm`/`k_norm` role variants if `TensorRole` lacks them — an
   additive enum change." It does not lack them. **No enum change was made, and
   `crates/q-source` was not touched** (it is also on this task's do-not-touch
   list).
2. **`architectures/llama/plugin.toml` already declares `self_attn.q_norm.weight`
   and `self_attn.k_norm.weight` rules.** `TASK.md` §Files Expected to Change
   permits editing `resolver.rs` "only if Qwen needs a pattern form Llama does
   not have (e.g. `q_norm`/`k_norm`, which Llama lacks)". Llama's *manifest* has
   the rule; only Llama *checkpoints* lack the tensor. So **no production Rust
   change was needed anywhere**, and none was made — the plugin schema already
   expressed every Qwen concept. That is itself the evidence for the crate doc's
   claim that adding a family is a manifest edit rather than a rewrite.
3. **`MatchKind::ExpertSuffix` requires `[naming].expert_segment`**
   (`crates/q-architecture/src/lib.rs:109-110`,
   `crates/q-nsir/src/resolver.rs:64-77`). The pre-existing Qwen manifest
   declared no `expert_segment`, so MoE addressing would have silently never
   fired. Added `expert_segment = "experts"`, asserted by
   `qwen_expert_rules_use_the_expert_match_kind`.
4. **`crates/q-report/tests/golden/manifest.v1.json:19` contains
   `"architecture": "qwen"`.** Checked before implementing, because a golden
   produced through plugin selection would have broken across a crate boundary.
   It is a **static hand-written document** that
   `crates/q-report/tests/schema_conformance.rs:466,710,724` only deserializes;
   no code path selects a plugin to produce it. `grep -rn
   "unresolved_count\|resolver_id" --include="*.rs" crates/ tests/` found every
   other assertion pinned to `"llama"` or `"generic"`. **No cross-boundary
   breakage.**

`the_moe_router_and_the_dense_mlp_gate_are_different_roles` asserts
`mlp.gate.weight` resolves to `MoeRouter`/`Component::Router` (row 4's point),
and `qwen_resolves_the_task_data_contract_examples` asserts
`AttentionQueryNorm` and `expert == Some(37)` alongside the literal addresses.

### One naming fact consulted from public convention

Qwen release differences (Qwen2 ships q/k/v projection **biases** with
`attention_bias: true` and no `o_proj` bias; Qwen3 drops the biases and adds
per-head `self_attn.{q,k}_norm.weight`; Qwen3-MoE routes with `mlp.gate.weight`
and holds experts at `mlp.experts.N.*`; Qwen2-MoE additionally has
`mlp.shared_expert.*` and `mlp.shared_expert_gate.weight`) are **not** determined
by anything checked into this repository, since no Qwen checkpoint is committed.
They come from the model author's published naming convention and are recorded
here as **advisory**. They are:

* **not** a build, runtime, or test dependency — every expectation is a checked-in
  literal or a checked-in fixture row, and no test reaches the network;
* **safe if wrong in either direction.** A name this manifest teaches that Qwen
  does not emit is a rule no tensor ever reaches, so it claims nothing. A name
  Qwen emits that this manifest does not teach resolves to `unknown`, which is
  the correct answer under `NSIR-001`. That asymmetry is why `TASK.md` §Risks
  records "unknown names return `unknown`, which is safe" as the mitigation for
  "Qwen naming varies across releases".

`mlp.shared_expert.*` and `mlp.shared_expert_gate.weight` are **deliberately not
taught** (`TASK.md` §Scope names `experts.N.*` and `mlp.gate.weight` only) and are
asserted to stay `unknown`. A shared expert is not a routed expert and must not be
addressed as one.

### An observed property of shared code that was NOT changed

`split_structure` (`crates/q-nsir/src/resolver.rs:64-77`) searches for the expert
marker with `suffix.find("experts.")`, which is not anchored to a path-segment
boundary. A name containing `mlp.shared_experts.0.up_proj.weight` (plural) would
therefore match inside `shared_experts.` and be filed as routed expert 0. **No
Qwen name triggers this**: Qwen2-MoE uses `shared_expert` (singular, unindexed)
and Qwen3-MoE has no shared expert, which is why the two singular spellings are
asserted `unknown` and pass. The plural spelling belongs to DeepSeek, whose
resolver is out of scope and unimplemented. This function is shared with the
Llama resolver, `TASK.md` gates `resolver.rs` edits on "only if Qwen needs a
pattern form Llama does not have", and Qwen does not. **Left unchanged and
reported here rather than fixed.**

## Summary

* **`architectures/qwen/plugin.toml`** — `implemented = false` → `true`, with 21
  rules and 21 aliases covering Qwen2 and Qwen3, dense and MoE. Added
  `expert_segment = "experts"` and the two MoE architecture strings. The rule
  table is a deliberate mirror of `architectures/llama/plugin.toml`, so the same
  raw name produces a byte-identical canonical address from either family.
* **No production Rust change.** `crates/q-nsir/src/resolver.rs` and
  `crates/q-architecture/src/lib.rs` gained tests and doc corrections only; the
  resolution engine, the `TensorRole` enum, and `schemas/nsir/schema.json` are
  untouched. `TASK.md` §Data Contracts predicted "no schema change is expected".
* **`fixtures/tiny-qwen-single/`** — a **naming** fixture: `config.json` (Qwen3
  declared config, for registry selection) and `golden.json` (21 raw names over
  the 15 families `TASK.md` §Scope lists, each with its hand-written canonical
  address, plus 6 names deliberately not taught). It carries **no weight payload
  and no `.safetensors` file**, because name resolution is what is under test and
  `resolve_name` takes a `&str` — a shape is not merely unused, it is
  unavailable.
* **25 tests added** (14 in `q-nsir`, 11 in `q-architecture`); 1 pre-existing test
  rewritten in place, as acceptance criterion 5 anticipates. Floor raised
  **434 → 459** over an unchanged 43 binaries.

## Architecture conformance

**Governing sections.**

* **`ARCHITECTURE.md` §4.2 (Architecture Plugins)** — the root rule: *"The
  resolver must be allowed to return `unknown`. It must never guess a semantic
  role just because two tensors share the same shape."* Satisfied structurally,
  not just behaviourally: `resolve_name` takes a `&str`, so a shape is
  unavailable to the code that decides a role. Asserted by
  `qwen_reads_names_only_so_two_identically_shaped_tensors_get_different_roles`
  (two descriptors with `assert_eq!(a.shape, b.shape)` resolving to different
  roles, and a third with the same shape resolving to `Unknown`).
* **`ARCHITECTURE.md` §6.1 (Canonical Address)** — the address form every
  expected literal in this task was written from.
* **`ARCHITECTURE.md` §6.2 (Contextual Alias)** — *"If `Att` could refer to Q, K,
  V, O … the query must return a list of candidates rather than silently picking
  one tensor."* The Qwen manifest declares `Att`, `Attn`, `MLP`, `Norm`, and the
  Qwen-specific `QKNorm` with more than one role;
  `an_ambiguous_qwen_alias_returns_candidates_not_a_silent_pick` asserts 4
  candidates for `Att[10]`, confidence `0.25`, declared role order preserved, and
  `AmbiguousAlias` from `unique()`.
* **`.plan/DATA_ARCHITECTURE.md` §4 (NSIR — canonical identity)** — names the
  three rules this task is measured against (a resolver may return `unknown`;
  never infers a role from shape; an ambiguous alias returns candidates) and
  establishes the canonical address as the universal join key, which is the
  argument that settled the three `TASK.md` spelling defects above.

**Binding ADRs.**

* **`ADR-010` — rank ≤ 3 implemented, rank > 3 refuses rather than flattens.**
  Rank is **not expressible** in a name resolver: nothing in this change sees a
  shape, so there is no rank to accept or refuse. The nearest expressible surface
  is the **number of axis labels a rule declares**, and
  `no_plugin_rule_declares_more_axes_than_the_implemented_rank_ceiling` asserts
  `axes.len() <= 3` for every rule of every plugin in the registry — a rule
  declaring four axes would be a manifest asserting a rank the rest of the system
  refuses to render. Every Qwen rule declares 1 or 2. **This is not a claim that
  this change enforces the rank ceiling**; `bindAxes()` owns that, and it is not
  in this task.
* **`ADR-004` / `.qtile` format, `ADR-009` world axes** — not reached. This change
  produces no artifact, no tile, and no geometry.

**Subsystem doc.** `.plan/DATA_ARCHITECTURE.md` §4, as above. No schema change:
`schemas/nsir/schema.json` already admits every value this resolver produces —
`Router` and `MoE` are in its `component` enum, and `AttentionQueryNorm` /
`AttentionKeyNorm` are in its `role` enum. `TASK.md` §Data Contracts states that
needing a schema change "would indicate the abstraction is family-specific"; none
was needed, which is positive evidence that it is not.

**Applicable `ARCHITECTURE.md` §19 checks.** §19 is about visualization, and most
of it is out of reach here — this change emits no GLB, stores no positions, sends
nothing to a browser, runs no Cesium, and executes no chat expression. The one
clause that binds is **"Do not assume a color pattern corresponds to a semantic
concept … Raw weight visualization only represents numerical structure; it does
not prove cognitive function."** Its generalisation binds directly: **a name
pattern is not a concept either.** The manifest header states this in the file
itself, and every claim in this record is about *where a tensor lives and what
its author called it* — never about what it means, has learned, or computes. §19's
performance clauses are also respected in passing: resolution is a linear scan of
21 rules per name with no allocation of any weight payload, so the 47 278-tensor
constraint in `TASK.md` §Memory and Performance Constraints is met by
construction (see `## Claim limits` — this was not benchmarked).

**`AGENTS.md` rule 4 (exact vs sampled vs approximate).** Every result this
change produces is labelled **exact**: a canonical address is a deterministic
function of the raw name and a declared rule table, with nothing sampled and
nothing estimated. `fixtures/tiny-qwen-single/golden.json` carries
`"fidelity": "exact"`, and the `q-nsir` crate doc now says so and says what it
does *not* mean. **Nothing here is sampled or approximate.**

  map to *these addresses*, and that names outside the table return `unknown`.

  A resolver maps **names**, and this change establishes only where a tensor
  lives and what its author called it. It does **not** establish what any tensor
  means, what it has learned, what it computes, or that a tensor labelled
  `query_projection` performs query projection — that label is the checkpoint

  colour pattern is not a semantic concept; **a name pattern is not one either**,

  cognitive function, capability, or behaviour is claimed for any weight,
  anywhere in this change.

  function of a raw name and a declared rule table. Nothing here is sampled or

### Ruling: the latent `experts.` issue in `split_structure`

**Real, correctly reported, and not blocking — recorded here for a follow-up
task.** The mechanism is confirmed by reading
`crates/q-nsir/src/resolver.rs:64-77`: the expert marker is built as
`format!("{seg}.")` = `"experts."` and located with an **unanchored**
`suffix.find(…)`. Because `"experts."` is a substring of `"shared_experts."`, a
name such as `model.layers.10.mlp.shared_experts.3.up_proj.weight` would yield
`expert = Some(3)` and `suffix = "up_proj.weight"`, which the manifest's
`expert_suffix` rule then files as **routed** expert 3 — a shared expert
addressed as a routed one, which is exactly the conflation
`architectures/qwen/plugin.toml:36-42` says must not happen.

What this repository proves, stated without overreach:

* The mis-filing is real in the code path, and the code path is **pre-existing
  and unmodified** — `split_structure` is byte-identical to `6fb593a` and is
  shared with the Llama resolver.
* The committed fixture and tests pin only the **singular** `shared_expert.`
  form (`crates/q-nsir/src/resolver.rs:1057-1060`, asserted at `:1070` via
  `unresolved_count() == 1`, and `QWEN_UNTAUGHT` in the generator). That form is
  safe: `"shared_expert."` does not contain `"experts."`, so it correctly stays
  `unknown`.
* Whether any real Qwen checkpoint emits the **plural, indexed**
  `shared_experts.N.` spelling is **not established by anything in this
  repository**, and the reviewer does not assert it either way. No test, fixture,
  or manifest in the tree contains such a name.
* The two other plugins that could reach the path are safe today: `generic` has
  no MoE rules at all (`generic_resolver_has_no_moe_rules_and_says_so`), and a
  `MatchKind::Suffix` rule additionally requires `expert.is_none()`, so a name
  that trips the substring match cannot fall through to a dense rule either.

So the residual exposure is a plugin that declares both `expert_segment =
"experts"` and `expert_suffix` rules meeting a checkpoint that uses the plural
spelling. `qwen` and `llama` both qualify structurally. **Follow-up task:** anchor
the expert marker on a segment boundary (require the preceding character to be
`.` or start-of-string) and add a test for the plural form. Not blocking here:
the defect is in shared pre-existing code that this task did not touch, `TASK.md`
§Files Expected to Change gates `resolver.rs` edits on Qwen needing a pattern
Llama lacks, and the implementer disclosed it rather than leaving it to be found.
