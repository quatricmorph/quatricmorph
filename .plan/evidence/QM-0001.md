## Summary

Nothing in this repository guarded the test floor. `scripts/` did not exist at
`793e122`; `.github/workflows/build.yaml` checked only exit codes, and QM-0006
had already demonstrated that an exit code alone is not enough — commit
`103297d` left vitest collecting 3 of 12 files while exiting 0.

This task adds `scripts/verify-baseline.sh`, the floor guard, together with
`scripts/baseline.json` (the recorded floor) and
`scripts/verify-baseline.test.sh` (46 unit tests over the guard's own parsing
and comparison logic). The guard runs the four Rust gates and the web suite,
parses the real counts out of both, compares them against the recorded floor,
and checks six CLI golden outputs against `fixtures/tiny-llama-2shard`.

Two floors are recorded per suite, not one. Alongside `rust_tests` and
`web_tests` the file records `rust_binaries` and `web_files`, because a test
binary that fails to build simply stops printing its `test result:` line and a
count-only floor would absorb the loss silently — the QM-0006 defect class in a
new dimension. The broken-test demonstration below shows both firing together.

**The floor recorded is `rust 290 over 39 binaries` / `web 115 over 13 files`,
measured in this worktree at `793e122`.** `STATUS.md`'s `101` is stale: it was
measured at `5ca434d` before QM-0006 repaired vitest's include globs. Both
numbers were re-measured here rather than copied.

The guard's own tests are deliberately **not** `cargo test` or `vitest` tests.
Adding them to either suite would raise the very counts the floor records and
make the floor self-referential; keeping them in shell lets the recorded floor
equal the measured reality exactly.

## Claim limits

1. **The recorded floor is a point-in-time measurement of `793e122`, and it is
   already stale relative to `main`.** The controller reports that `QM-0012`
   merged to `main` as `4e0e85c`, adding 28 Rust tests, and that `main` now
   measures **318 passed** at `9a5398d`. This worktree was cut before that merge
   and correctly measures **290**. `318` is **not verifiable from here and is
   deliberately not written into `scripts/baseline.json`** — recording an
   unverified number is the failure mode this whole task exists to prevent.
   **The controller will re-measure on the merged `main` and correct the
   committed floor in the same squash commit at merge time.** Until that
   correction lands, the floor will sit 28 below reality on `main`, which the
   guard will report as `FLOOR IS STALE by 28` (§10) while still exiting 0.

   **Updated by §12:** the 318 is no longer second-hand. A trial merge with
   `main@ae600c9` inside this worktree measured `318 passed; 0 failed; 0
   ignored; 39 binaries` and web unchanged at `115/13`, with the guard exiting
   0 and every CLI golden intact. `scripts/baseline.json` is still committed at
   290 — the merge was aborted, not committed, and the merge-time correction
   remains the controller's. **The harness compares with `-ge`, not equality, so
   raising `rust_tests` to 318 requires no change to
   `scripts/verify-baseline.test.sh`.**
2. **A floor below reality is not a failure — this is the guard's central blind
   spot.** The comparison fires only when the floor *exceeds* the real count.
   Below reality it is silent about the gap: tests in the gap could be deleted
   and the guard would stay green. Two partial mitigations, neither of which
   closes it: the run *reports* the staleness with both numbers and the size of
   the gap (§10), and the harness hard-codes `290/39/115/13` so the file cannot
   record **less than the 793e122 baseline**. It does **not** prevent a later,
   higher floor from being lowered back down to that baseline. That remains a
   review rule, exactly as the task's Data Contracts section states.
3. **The floor is only as honest as the run that recorded it.** These numbers
   were measured on a tree where both suites collected fully — 39 binaries and
   13 files, both recorded as structural floors precisely so that a *future*
   under-collecting run cannot quietly re-record a smaller floor. But that
   protection is only as good as the structural numbers themselves, which were
   in turn measured on this run.
4. **`baseline.json` is validated by a targeted extractor, not a JSON parser.**
   It checks brace balance, quote parity, a leading `{`, and the presence and
   type of every required key. It would accept some inputs a real parser
   rejects — for example duplicate keys or a misplaced comma between two
   otherwise valid pairs. `jq` was available locally but deliberately not used,
   to keep the guard dependency-free. The three malformations that matter in
   practice (absent, truncated, non-numeric floor) are each covered by a test
   and §5 exercises truncation for real.
5. **The runtime figures are warm-cache figures and AC-6 should be read with
   that caveat.** 82 s partly-cold, 13 s fully warm, both far under 300 s. But
   the guard re-runs `fmt`, `clippy`, `build` and `test` that the CI job has
   *already* run, roughly doubling the `rust` job's work, and QM-0006 measured a
   cold `cargo clippy --workspace --all-targets` at **3 m 56 s** on this
   machine. A cold CI run could therefore approach or exceed the 5-minute
   budget. The script measures and prints its own elapsed time and warns past
   300 s, so this will be observable rather than silent. The duplication is as
   the Implementation Plan specifies ("wire it into CI after the existing test
   step"); collapsing it is a CI-shape change this task's Out of Scope forbids.
6. **AC-5 is half-evidenced.** CI *invokes* the script — verified by re-parsing
   the YAML and confirming step order (§11). CI *passes* is not verified; no
   workflow run was observed, and none can be from this repository.
7. **`cargo fmt`, `clippy`, `build` and `test` results are properties of the
   base commit, not of this change.** This task adds no Rust and no TypeScript.
   They are recorded to show the floors did not move, not to claim anything new
   about the code.
8. **The guard proves counts and goldens; it does not prove correctness.** It
   would stay green against 290 Rust tests that all assert `true`. It is a floor
   and a set of golden values, not a substitute for review — the task's own
   Risks table makes the same point.
9. **Two Node majors, not the one CI pins.** The vitest half of the floor was
   measured on this machine's Node 23.7.0. `.github/workflows/build.yaml` pins
   Node 22. The collection counts come from vitest's own matcher and are
   Node-independent, but as QM-0006 recorded, Node 22 is not installed here and
   was not tested.
10. **`bash` 3.2 was the only shell tested.** Both scripts are written to
    bash 3.2 (no associative arrays, no `mapfile`) because that is the macOS
    system bash, and were run under it throughout. CI's `ubuntu-latest` provides
    bash 5, which is a superset for every construct used, but that was not run.
