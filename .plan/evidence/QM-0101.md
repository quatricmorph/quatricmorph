## Summary

**G1 passes.** The full statement, with the part that decides it in bold:

> Streaming 327,404,544 payload bytes of `models/distilbert-distilgpt2` through
> the bounded block reader, against a resident ceiling **`C = 3,528,244 B`
> declared in `.plan/DEFINITION_OF_DONE.md` `V1-04` and derived from the
> checkpoint's size rather than from any measurement**, the release binary's peak
> resident set size was **3,850,240 B — the largest of 20 runs — against a
> tolerance of 4,410,305 B**, a margin of 560,065 B (12.70 %). `N = 100.0000037`.
> `C` is 608.7× under the plan's `C ≤ 2 GiB`.

`QM-0100` was ruled near-tautological because its ceiling was `C = R / 1.25`,
back-solved from the measured peak, which makes `peak ≤ 1.25 × C` an identity.
Three things changed here, and together they are the substance of this task:

1. **A configured resident ceiling now exists.** `MAX_RESIDENT_BYTES` (2 GiB
   compiled default) in `crates/q-source/src/budget.rs`, plus
   `.plan/MEMORY_BUDGET.md` §11's precedence chain — CLI flag > environment >
   config file > compiled default — which was **unimplemented** before this task
   and is now `crates/q-source/src/config.rs`. Every ceiling this evidence quotes
   is declared in a file checked into the repository *before* the run that
   measured against it.
2. **The comparison is falsifiable, and was seen to fail — twice.** At the
   *measurement* level: the same binary, same checkpoint, same ceiling, with
   `--io mmap`, peaks at 331,038,720 B, **75.07× over the tolerance**, in every
   one of 13 runs. At the *admission* level: `--resident-ceiling 1MiB` exits 1
   with `memory budget exceeded [max_resident]: requested 1574912 bytes, limit
   1048576 bytes`, before reading a byte. Both are automated
   (`the_mapped_read_mode_breaches_the_same_ceiling_so_the_gate_is_seen_to_fail`).
3. **A checkpoint-level pass exists to measure.** `QM-0030` bounded one *tensor*;
   `crates/q-tensor-runtime/src/residency.rs` bounds a *checkpoint*, and
   `q stream` is the verb that runs it.

Three findings worth a reviewer's attention:

* **The mmap path could not have held any ceiling, and that is why the read mode
  changed.** Mapped pages count toward RSS while resident
  (`.plan/MEMORY_BUDGET.md` §3), so a mapped pass over a 337 MiB file reports
  ~331 MB of RSS while holding 1,574,912 B of buffers. `TASK.md`'s Risks table
  anticipated this and forbade redefining the metric to pass. The answer taken
  was `ReadMode::Pread` — **opt-in**, so `q value`, `q slice` and `q stats` keep
  mapping and keep the behaviour they were written against. It is now also the
  most useful negative evidence in the task.
* **Acceptance criterion 1 is only PARTIALLY met and must not be read otherwise.**
  56 of 82 tensors are refused — 50 rank-1 and 6 rank-4 — **correctly**, under
  `ADR-010`. 92.80 % of the described payload streams. Making rank-1 streamable
  to close the gap would have meant deleting
  `refuses_rank_one_rather_than_inventing_a_second_axis`, i.e. weakening a passing
  test to pass a gate. Instead the refused bytes are reconciled:
  `327,404,544 + 25,411,584 == 352,816,128` exactly.
* **`N ≥ 100` is true by construction at this ceiling and I say so plainly.**
  `C = ⌊checkpoint_bytes / 100⌋`, so `N = 100` is arithmetic. The falsifiable
  content of G1 is the third conjunct, `peak ≤ 1.25 × C`. This is a materially
  different situation from `QM-0100`'s — there, the *measurement* comparison was
  the tautology; here it is the one thing that could have failed, and the mmap row
  proves it.

Two of my own mistakes are recorded rather than quietly fixed, both caught **by
the tests I had just written**: a hand-computed `ratio_n` that was wrong in the
sixth decimal place, and a `next_block_index` that reported 1243 instead of 100
after cancelling at block 100. Both are under *Validation evidence*.

### Why criterion 1 cannot be fully met, in one paragraph

`BlockStream` needs a 2-D extent. `models/distilbert-distilgpt2` holds 50 rank-1
tensors (biases, layer norms) and 6 rank-4 causal masks `[1, 1, 1024, 1024]`.
`ADR-010` is `Accepted` and requires rank above 3 to **refuse rather than
flatten**; rank-1 display is `QM-0061`'s axis-binding work and rank-3 is
`QM-0040`'s. So a pass that streamed "every tensor" would either be flattening
(forbidden) or would need work outside this task's boundary. What is achievable
and is delivered: every byte of every *streamable* tensor, exactly once,
checksummed, with the remainder refused by name and reconciled to the byte.
`--require-all-tensors` exists and exits 1 on this checkpoint — proving the
refusals are real rather than silently tolerated.

## Claim limits

**Is the ceiling configured independently of the measurement?** **Yes**, and this
is the question the task turns on. `C = 3,528,244` is `⌊352,824,413 / 100⌋`,
arithmetic over the checkpoint's size as recorded in
`fixtures/real-checkpoint-record.json` and as required by
`.plan/DEFINITION_OF_DONE.md` `V1-04`. It is **not** `R / 1.25`, which is what

`the_g1_ceiling_is_derived_from_the_checkpoint_size_and_never_from_a_measured_peak`
asserts the two differ. The compiled default (2 GiB) is more independent still —
it predates any measurement entirely — and is also reported, together with the
fact that `N` fails at it.

**Which conjunct is true by construction, and which is measured.** `N ≥ 100` is
**true by construction** at this ceiling: choosing `C = checkpoint/100` makes
`N = 100` arithmetic, not a finding. The falsifiable content of G1 is
`peak ≤ 1.25 × C`, and it is falsifiable in practice as well as in principle —
the same ceiling is breached 75.07× by `--io mmap` in every one of 13 runs.
`C ≤ 2 GiB` is trivially satisfied at 608.7× under.

**Scale.** The checkpoint is **352,824,413 B (~337 MiB), a single file with no
`model.safetensors.index.json`** — not the ≥ 24 GB sharded checkpoint the plan
originally wanted, and about 1/70th of it. G1 is established at `C = 3.365 MiB`
on a 337 MiB file, **not** at `C ≤ 2 GB` on a ≥ 24 GB file. Those are different
claims and this one must not be reported as the other.
`crates/q-catalog/tests/trillion_scale_manifest.rs` is metadata-only, opens no
artifact, and may never substitute for this.

**The sharded read path at scale is not established.** Multi-shard streaming is
exercised only by `fixtures/tiny-llama-2shard`, at 1.2 MB. v1 must not claim
real-checkpoint shard coverage.

**This is streaming, and it establishes nothing about throughput.** Elapsed times
appear because they were observed: the page cache was warm, no run was repeated
cold, nothing was pinned, and the read mode that wins on residency (`pread`) is
*slower* in wall clock than the one that loses (0.69 s vs 0.44 s on the same
work). A residency measurement says nothing about how fast bytes move. `QM-0102`
owns that and nothing here should be quoted toward it.

**Not every tensor streams, and 92.80 % is not 100 %.** 26 of 82 tensors, 92.80 %
of the described payload. The remaining 25,411,584 B are refused under `ADR-010`
and reconciled to the byte. "The whole checkpoint streams" is **false** as stated
in acceptance criterion 1 and is recorded as partially met.

**mmap page-level residency is unmeasured.** No `vmmap` or `mincore` measurement
was taken. What is measured is that the mapped mode drives *process* RSS to
~331 MB while its own footprint stays at ~2.4 MB. The G1 figure covers the
**pread** streaming path only: `q value`, `q slice`, `q stats` and every other
mapped consumer **do not inherit this bound**, and a residency claim about them
would need its own measurement.

**Peak RSS is approximate, and the exact figure is a different metric.** RSS is
sampled by the kernel and includes binary text, stacks and allocator arenas; it
moved by up to 327,680 B between identical runs, which is why every row records a
range and a sample size. The counting-allocator heap figure is **exact** and
deterministic but sees neither mapped pages nor stacks. Neither is presented as
the other.

**No GPU, deployment, or partner claim.** No CUDA or Metal code runs in this
pass; `q-cuda` remains `Hardware-Unverified`. Nothing here is a statement about
any device, any deployment, any customer, or any partner.

**No semantic claim about weights.** The checksum proves bytes were read at known
positions. It says nothing about what any weight means, and `q stream` runs no
resolver at all, so every tensor's role stays `Unknown` by construction.

**`models/` is gitignored, so this repository redistributes no weights.** The
checkpoint is a local input, not a shipped artifact.

  accounting: `6 × 262,144 + 256 × 8 = 1,574,912`, where `6 = queue_capacity(4) +
  2`.

**5. What this pass establishes.** That a checkpoint-level streaming pass over
352,824,413 bytes holds a **3,528,244 B** ceiling at a measured peak RSS of
3,850,240 B (implementer, worst of 20) / **3,833,856 B** (mine, worst of 12), and
that its residency is **flat**: the *exact* counting-allocator peak is
1,053,015 / 1,102,726 / 1,084,769 B across a **3,331×** span of checkpoint size —
byte-identical on every run I took, and 4,248,454 B at 512×512, which proves the
figure tracks the configured block size rather than being a fixed floor. The
flatness result is the strongest number in this task and it is exact, not
approximate.

**6. What it does not establish**, and the evidence says each of these plainly:
not `C ≤ 2 GB` on a ≥ 24 GB checkpoint (no such file exists here; at 2 GiB `N` is
0.164 and this checkpoint would need to be 200 GiB); not sharded streaming beyond
the 1.2 MB fixture; not mmap page-level residency; not the mapped path at all, so
`q value` / `q slice` / `q stats` **do not inherit this bound**; nothing about
throughput, GPU, deployment, or meaning.

**7. One caveat of my own that the evidence does not state.** At `C = 3.365 MiB`
the tolerance is `4,410,305 B` while the process's *fixed* cost — binary text,
stacks, allocator arenas — is about 2.3 MB (`peak memory footprint` reads
2,277,688 B in my run against 1,574,912 B of accounted buffers). So roughly 60 %
of the ceiling is consumed by things that have nothing to do with streaming, and
the 576,449 B of headroom I measured would be erased by unrelated growth in the
binary. That makes the gate **falsifiable for the wrong reason** as well as the
right one: a future G1 failure at this ceiling should be bisected against binary
size before it is read as a streaming regression. This does not weaken the pass —
it is a consequence of pinning `C` to `checkpoint / 100` on a 337 MiB file, which
`V1-04` required — but a later reader should know it.

### Flake risk — my judgement

`the_release_binary_holds_the_configured_ceiling_over_the_real_checkpoint`
re-takes an RSS measurement inside the suite and asserts `≤ 4,410,305`. **I judge
it acceptable as a test, for four reasons**, and I would not ask for it to be
demoted to a reported figure: my 12 runs spread only **65,536 B**
(3,768,320 … 3,833,856) against **576,449 B** of headroom — about 8.8× the
observed spread; it is gated on both a release binary and the real weights, so it
cannot fire spuriously on a machine that has neither; its panic message names
`.plan/EXECUTION_ORDER.md` §7 and says *"do not raise C to make this pass"*, which
is the correct instruction to leave at a failure site; and the alternative — a
figure in a JSON file with nothing re-measuring it — is precisely how `QM-0100`'s
claim became unfalsifiable.

Two limits on that automation, which a later reader should know. First, CI is
`ubuntu-latest` (`.github/workflows/build.yaml:18`) and has neither `models/` nor
a release binary, so on CI **both** live-RSS tests take the early `return` and
G1's automated enforcement reduces to record-consistency over a committed JSON
file. Live re-measurement happens only on a macOS/BSD developer machine that has
the weights. Second, `peak_rss_of_stream` `.expect()`s `/usr/bin/time -l`, so on a
Linux machine that *did* have the weights and a release binary these two tests
would hard-error rather than skip. Neither is a defect in this branch — the
`.expect` message shows the author knew — but neither should be mistaken for CI
coverage of G1.

### `.plan/MEMORY_BUDGET.md` §11 — the new configuration surface

Reviewed `crates/q-source/src/config.rs` as new surface. The chain is
table-driven from one `VARIABLES` array, so the accepted key set, the environment
reader, the config validator and the "accepted keys" error message cannot drift
apart. Precedence is resolved **per variable** — flag > `QM_`-prefixed env > file
> compiled default — which is the correct reading of §11's *"Every variable above
is settable, in this precedence order"*. The zero check is applied at every link,
including the already-parsed flag. A named-but-unreadable file is an error rather
than a skip, and is read even when every variable comes from a flag — stricter
than necessary and the right way round. An unknown key under `[budgets]` is
refused **naming the accepted keys**, on the stated ground that a budget which
silently did not apply cannot be told from one never set. `EnvLookup` is a trait
specifically so tests exercise the environment link without
`std::env::set_var` racing the other threads in the binary — a real
flake avoided rather than tolerated. Provenance rides along with each value and
round-trips through serde, which is what §11 asks for. I found nothing to change.
