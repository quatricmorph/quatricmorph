### `StatisticsId` — the byte layout, and a contradiction resolved

`TASK.md` cites `ADR-CANDIDATE-018`, which was **promoted** to
`docs/decisions/ADR-011-content-derived-identifiers.md` on 2026-08-04
(`.plan/PLAN_CHANGELOG.md:434`, `.plan/decisions/README.md:85`). ADR-011 is
therefore the governing decision and was read in full.

ADR-011 specifies `StatisticsId` two ways, and they produce **different
digests**:

| Source | Rule |
| --- | --- |
| ADR-011 §Decision construction rule | fixed-width components (`[u8;16]`, `u32`) appended **without** a length prefix |
| ADR-011 §Consequences | `blake3("quatricmorph/statistics/v1" ‖ subject_id ‖ algorithm_version_le)[..16]` |
| `TASK.md` §Scope | `blake3(len‖subject_id ‖ len‖algorithm_version)` — **prefix both** |

The tie-breaker is the shipped code ADR-011 claims to codify.
`q_source::ids::digest16` (`crates/q-source/src/ids.rs:81-94`) length-prefixes
**every** part it is handed, and `TensorId::derive` hands it
`model.as_bytes()` — a `[u8; 16]`, i.e. a fixed-width component — which is
therefore length-prefixed in already-persisted `TensorId`s. So ADR-011's prose
rule contradicts its own reference implementation, while `TASK.md` §Scope agrees
with it exactly.

**Implemented `TASK.md` §Scope / the shipped `digest16`: both components
length-prefixed.** Matching the shipped construction is what makes this a
*fourth kind in one scheme* rather than a second scheme. Recorded here rather
than chosen silently, because ADR-011 says itself that this freezes "the moment
it runs".

### Where the code lives, and why not in `q_source::ids`

ADR-011 says new ID kinds are added through `q_source::ids`' `define_id!` macro.
`q-source` is outside this task's boundary and is concurrently owned by
`QM-0030`, so `StatisticsId` is implemented in `q-catalog` instead —
**byte-identically**. `q_source::ids::ID_SCHEME_VERSION` is `pub` and is imported
rather than re-spelled; `digest16` and `define_id!` are private, so the
construction is reproduced. `statistics_ids_follow_the_shipped_digest_construction_byte_for_byte`
pins the result to a literal derived from ADR-011's byte layout, so relocating
this into `q_source::ids` later provably changes no persisted ID. Follow-up for
whoever owns `q-source` next; it is a code move, not a behaviour change.

The ulp-level differences in `mean`, `variance` and `l2_norm` are **summation
order**, not error: `q-statistics` accumulates with Welford in a single
streaming pass, NumPy uses pairwise summation. Both are f64 over the same f32
inputs. The histogram matching bin-for-bin is the strongest of these checks —
any binning, stride, or endianness mistake in the blob codec would have shown
there.

**This did not change the implementation.** It confirmed it, and it is the
evidence for the claim that the persisted numbers are exact over their subject
rather than merely self-consistent.

`blake3` has no Python binding in the venv and no `b3sum` is installed, so the
`StatisticsId` golden is pinned by a second, independent transcription of
ADR-011's byte layout inside the test (`statistics_id_reference`) rather than by
a foreign tool. The hash *primitive* is shared; the *construction* — which is
what is under test — is derived twice, independently.

### The schema decision, stated as a decision

A schema change **was** needed and was taken deliberately, not silently:
`subject_kind` is in `TASK.md`'s data contract, is named a column by ADR-011
point 2, and did not exist. Migration 2 is appended, never edited into migration
1, per `.plan/DATA_ARCHITECTURE.md` §3.2 ("a shipped migration has already run on
someone's disk"). It is `ALTER TABLE ADD COLUMN` rather than a rebuild because a
`DROP`/recreate cannot prove inside SQL that it is destroying nothing.

The default is `'unknown'`, not `'tensor'`. A row written before the column
existed has no recorded kind, so `SubjectKind::parse` **refuses** `'unknown'` and
such a row is rejected as malformed rather than reinterpreted — the same
discipline `SRC-014` applies to unknown dtypes and `NSIR-001` to unknown roles.
Asserted by `migrating_a_version_one_database_adds_subject_kind_without_losing_a_row`
(a hand-written v1 row survives migration and reads as `unknown`) and
`a_row_whose_subject_kind_was_never_recorded_cannot_be_read`.

The `histogram` column is **not** migrated. Migration 1 declares it `TEXT` with a
`-- JSON` comment; this build writes a length-prefixed little-endian blob there.
SQLite's TEXT affinity stores a BLOB value as a BLOB unchanged, asserted by
`the_persisted_histogram_is_a_little_endian_blob_not_json` reading
`typeof(histogram)`. A `TEXT` value in that column is **refused with a reason**
(`a_row_whose_histogram_is_not_a_blob_cannot_be_read`), which is a stronger
guarantee than a column-type change would have bought: refuse rather than
reinterpret.

### Blob layout, and the byte arithmetic

```text
u32          bins        length prefix; 0 = "no histogram was computed"
f64          min
f64          max
bins × u64   counts
```

`20 + 8 × bins` bytes — **532** for the 64-bin default, not the flat 512
`TASK.md` §Memory and Performance Constraints quotes. 512 is the counts alone;
the 20-byte header carries the length prefix the same section asks for plus the
range the counts are meaningless without. Little-endian on every host, matching
`.qtile` (`.plan/DATA_ARCHITECTURE.md` §6), asserted byte-by-byte rather than
assumed.

`MAX_HISTOGRAM_BINS = 256` (2 068 B/row). The design point is 64 bins = 532 B,
which at the ~47 000 tensors of `tests/trillion_scale_manifest.rs` is 25 MB —
what keeps `q-catalog`'s "the catalog is tens of megabytes" claim true. The
ceiling is 4× that, 97 MB at the same row count, and a request above it is
refused rather than truncated.

## Architecture conformance

**Governing sections.** `ARCHITECTURE.md` §5.4 (statistics table), §13.2
(`algorithm_version` in the cache key), §14.1 (metadata API), §18 `AC-010`
(exact / sampled / approximate must be indicated), §19.

**Binding ADRs.**

* **`ADR-003` — SQLite for the metadata catalog.** Governs, and
  `ARCHITECTURE.md` §5's DuckDB/Arrow/Parquet does not. Every statement written
  here is `rusqlite` SQL against the SQLite schema in
  `crates/q-catalog/src/schema.rs`; no Parquet or Arrow is produced. ADR-003's
  §Consequences names the trigger to revisit itself — *"Analytical queries (§7.3
  `GROUP BY layer_index`, aggregate norms) will be slower on SQLite **once
  statistics exist**"*. This task is what makes statistics exist, so that
  trigger is now armed. `GROUP BY` queries are `QM-0072` and explicitly out of
  scope here; the reads this task adds are point lookups on the indexed
  `subject_id`, which is ADR-003's strongest case, so nothing here forces the
  revisit yet. Flagged for the controller.
* **`ADR-011` — content-derived 128-bit identifiers.** `StatisticsId` follows it
  (domain `quatricmorph/statistics/v1`, `subject_id` + `algorithm_version`,
  16-byte truncation, bare lowercase 32-hex persisted form). `subject_kind` is
  **not** hashed (point 2). Changing the algorithm mints a new row (point 1).
  Two documented departures, both recorded above and both deliberate: the
  length-prefix contradiction inside ADR-011 itself, resolved toward the shipped
  `digest16`; and the code living in `q-catalog` rather than `q_source::ids`
  because `q-source` is out of boundary.
* **`ADR-010` — rank ≤ 3, refuse above.** `q stats --persist` on a rank-1 tensor
  refuses with *"block extents apply to rank-2 tensors; got rank 1"* and writes
  nothing (`q_cli::tests::persisting_statistics_for_a_rank_one_tensor_is_refused_not_flattened`).
  The same guard refuses rank 4. No tensor is reshaped, flattened, or
  reinterpreted to make a statistic computable.
* **`ADR-004`** (`.qtile` little-endian on every host) is the precedent the
  histogram blob's byte order follows; the format itself is untouched.

**Subsystem docs.** `.plan/DATA_ARCHITECTURE.md` §3 (the `tensor_statistics`
row), §3.1 (this task named as the filler of "`tensor_statistics` is never
written"), §3.2 (migration policy — followed), §5 (`StatisticsId` derivation),

### ADR-011 adjudication — the length-prefix contradiction

**The contradiction is real, and matching the code was the correct resolution.**

`docs/decisions/ADR-011-content-derived-identifiers.md:49-52` states that
fixed-width components (`u8`, `u32`, `i64`, `[u8;16]`) are appended with "no
prefix". Its reference implementation does the opposite:
`crates/q-source/src/ids.rs:86-92` length-prefixes **every** part it is handed,
unconditionally, and `TensorId::derive` (`ids.rs:125-128`) hands it
`model.as_bytes()` — a `[u8;16]`. Every `TensorId` already persisted is therefore
prefix-both. ADR-011's justifying sentence (`:56-57`) cites `TileId` and
`CacheKey`, and those two genuinely do append bare — but neither goes through
`digest16` (`TileId::for_block` at `crates/q-tensor-runtime/src/lib.rs:264-280`
omits `ID_SCHEME_VERSION` entirely, which ADR-011 itself acknowledges and
freezes). So the prose rule describes two constructions the ADR excludes from
extension, while the one it mandates extending contradicts it.

Three things converge on prefix-both, and I verified each independently:

1. `digest16` prefixes unconditionally — read directly at `ids.rs:86-92`.
2. `TASK.md` §Scope writes the layout out explicitly:
   `blake3(len‖subject_id ‖ len‖algorithm_version)`.
3. ADR-011 says new kinds are added through `define_id!` in `q_source::ids` —
   which *is* `digest16`. Choosing the prose rule would have produced an ID that
   `define_id!` could never reproduce, i.e. the second grammar the ADR exists to
   prevent.

**Consequence for persisted IDs.** Because the construction matches `digest16`
byte for byte, the identifiers frozen by this task are exactly what a future
`define_id!(StatisticsId, "quatricmorph/statistics/v1", …)` in `q_source::ids`
will emit. The choice is therefore not merely defensible — it is the only choice
that keeps the eventual relocation free of a migration.

**The pinned literal is not the code asserting it equals itself.** I re-derived
BLAKE3 from the specification in Python (single-chunk; the hash input here is
exactly 64 bytes), validated my implementation against four published BLAKE3 test
vectors (empty, 3-byte, 64-byte, 1023-byte), then computed both candidate
layouts:

### Ruling on `aggregate` against `.plan/DATA_ARCHITECTURE.md` §8

**Sanctioned. Not an invented fourth label.** §8's table
(`.plan/DATA_ARCHITECTURE.md:218-224`) enumerates five fidelities, and row 2 is

§8's monotonic-degradation rule (`:229-230`, "a statistic over quantized data is

`CpuBackend::block_statistics` reads checkpoint bytes through `ModelSource` byte

**The mapping is total, invertible, and singly-spelled.** `from_approximate` and
`is_approximate` are mutual inverses over both `bool` values
(`the_fidelity_mapping_is_total_and_cannot_disagree_with_the_flag`). I grepped the

`StatisticsFidelity::as_str`; every other occurrence is a test assertion or a
doc comment. `q-catalog`, `q-daemon` and `q-cli` all call through

`the_wire_fidelity_is_the_single_mapping_not_a_re_spelled_literal` asserts the
route's value equals `StatisticsFidelity::from_approximate(flag)` for **both**
flag values rather than a duplicated literal — the requirement, met literally.

**`sampled` is wired but unproduced, and this is disclosed.** `mark_approximate`
has no non-test caller anywhere in `crates/`. §Claim limits states this
explicitly. No path can emit `aggregate` for a genuinely sampled statistic: the

### The partial-window rule — genuinely pinned

**Yes, and it is the right call.** `StatsSubject::of`
(`crates/q-cli/src/main.rs`) returns `SubjectKind::Tensor` only when the extent
starts at `(0,0)` and reaches both dimensions; `clamped_to`
(`crates/q-tensor-runtime/src/lib.rs:180-185`) has already capped `row_end` /
`column_end` at the shape, so the `>=` test can only be satisfied by exact
equality. Anything smaller becomes a `SubjectKind::Block` under
`TileId::for_block(tensor_id, Lod::Block, extent)` — the same `BlockId` the tile
plane uses, so the catalog row and the artifact address are one identity.

Two tests pin both directions:
`a_partial_window_is_persisted_as_a_block_never_as_the_whole_tensor` (asserts the
4×4 window is a block, that its subject id differs from the `TensorId`, **and
that `get_statistics(tensor_id, 1)` is `None`** — the window is unreachable as
the tensor) and `a_window_covering_the_whole_tensor_is_persisted_as_the_tensor`
(`count == 6144`, 64 bins, subject id equals the `TensorId`). Labelling 16 of
6,144 weights as the tensor's statistics would have been the honesty failure
`AGENTS.md` rule 4 forbids, and `TASK.md`'s own §Suggested Command consequently
writes a block row — disclosed rather than glossed.

**Ruling with its residual.** The guarantee lives at the CLI layer, which is the
only layer holding the tensor's shape; `Catalog::put_statistics_batch` cannot
enforce it and does not pretend to. That is the correct placement. See §Remaining
risks for the successor-task exposure.
